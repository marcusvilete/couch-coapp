# A Linux host on a real desktop

WSL builds and tests the Linux host (the `linux-checks` skill), but has no desktop session: no screen-sharing portal, no global shortcuts, no notification server of its own, no real sound device. This is the run on a real one. **Optional:** nothing in the build, the tests or CI needs it, and a missing VM never blocks a commit or a milestone (`milestone-wrap-up` lists it as optional). What isn't tried stays in the results page's "Still to come".

## Before: is there a desktop to run on?

1. Look first, assume nothing: `& "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe" list vms` (VirtualBox installed, and which VMs), or ask whether the author has a Linux PC or a Steam Deck to hand. A Linux PC or the Deck's Desktop Mode works with this checklist as it is (skip "Once").
2. **None:** say what one costs, then ask; never install anything unasked. VirtualBox (an installer and an admin prompt), an Ubuntu ISO of about 6 GB, about 25 GB of disk, an hour (most of it unattended), and the author at the screen for the installer's questions, the first sign-in and every dialog in the checklist. The alternative: run only what WSL can (`linux-checks`) and leave the rest in "Still to come".
3. Check the disk first (`Get-PSDrive C`): `target\debug` has filled C: twice.

## Once: make the VM (VirtualBox)

Done on the author's PC on 2026-11-03: VirtualBox 7.2.22, the VM `couch-linux` in `C:\Users\<user>\VirtualBox VMs` (the SSD; a VM's disk on the PC's hard drive, D:, would be sluggish), its snapshot "clean, tools in". To make it again:

- **The system: Ubuntu 26.04 LTS** (26.04.1 then), the desktop ISO from `releases.ubuntu.com/26.04/`, its SHA-256 checked against that folder's `SHA256SUMS`; kept on D:, read once. Its GNOME (48 or later) has the global-shortcuts portal; Ubuntu 24.04's GNOME 46 doesn't, so 24.04 can't test the host's keys on GNOME. Its packages match `scripts/linux-deps.sh`.
- **The VM:** `.\scripts\vm\create.ps1 -Iso <the ISO>` (VirtualBox installed first; its installer resets the network for a moment). 4 CPUs, 8 GB of memory, a 40 GB disk marked as an SSD with discard, EFI, VMSVGA graphics with 3D and 128 MB of video memory (Wayland needs it), sound out, the network **bridged** to the PC's wired adapter (so a Windows guest on this PC reaches it directly; NAT works too, through a relay).
- **Sound: AC97 through DirectSound.** On this PC Hyper-V is on (WSL2 needs it; never turn it off), and VirtualBox runs on top of it: WASAPI made the sound choppy, Intel HD Audio made it noise. The script sets AC97 and DirectSound; changing either needs the VM powered off.
- **Install** with the defaults (Interactive, Default selection, no proprietary drivers or media formats: the VM has no NVIDIA card, and nothing here needs them; Erase disk is the VM's own). Then the Guest Additions, typed by hand (no shared clipboard before them): `sudo apt update && sudo apt install -y build-essential bzip2`, Devices → Insert Guest Additions CD image (the VM window's menu, Right Ctrl+Home if hidden), then `sudo sh /run/media/$USER/VBox*/VBoxLinuxAdditions.run` (26.04 mounts discs under `/run/media`, not `/media`), and `reboot`.
- **Then, pasted:** `sudo apt full-upgrade -y`, and `sudo apt install -y kde-plasma-desktop evtest pipewire-bin pulseaudio-utils supertuxkart openssh-server`, choosing **gdm3** when asked (it keeps Ubuntu's login screen, whose sessions menu picks "Ubuntu", GNOME, or "Plasma (Wayland)"). SuperTuxKart: a native game with sound that reads controllers through SDL. `openssh-server`: copying builds in and logs out from Windows. GNOME runs a little smoother than KDE in the VM.
- **Keep it reusable:** the snapshot "clean, tools in" (taken powered off, the ISO ejected), and back to it before a run that installs a new build. The VM's disk lives in VirtualBox's folder, never in the repository. Keep one or two snapshots: each grows the disk on C:.

## Each run

**SSH into the VM** (set up 2026-11-03; a snapshot from before it needs it again): a key of its own on this PC, `ssh-keygen -t ed25519 -N '""' -f $env:USERPROFILE\.ssh\couch-linux`; with the VM running, share the folder holding only its `.pub` (`VBoxManage sharedfolder add couch-linux --name couchkey --hostpath <folder> --readonly --transient`), and the author pastes into the VM's terminal `sudo mount -t vboxsf couchkey /mnt && mkdir -p ~/.ssh && cat /mnt/couch-linux.pub >> ~/.ssh/authorized_keys && chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys && sudo umount /mnt && sudo systemctl enable --now ssh && hostname -I && whoami` (bridged: its IP is on the LAN, 192.168.15.39 then). Then from the Bash tool, `ssh -i ~/.ssh/couch-linux -o BatchMode=yes <user>@<ip> 'bash -s' <<'EOF' … EOF`: through PowerShell, quotes and `$` get mangled. Never a GUI program over SSH (no display: `plasmashell --version` crashed and brought up Ubuntu's crash dialog in the VM); the app is started by the author in the VM's session, or at sign-in.

**Get the build in:** an AppImage from the branch, built as the `release-installer` skill says (`bash scripts/build-appimage.sh --test-relay` from `~/couch-release`, the branch checked out there; uncommitted changes go in as a patch, `git diff --binary --output=<file>` on Windows with new files `git add -N` first, then `git apply` in the clone: a dirty test AppImage is allowed), copied in with `scp -i ~/.ssh/couch-linux <AppImage> <user>@<ip>:couch/`; `chmod +x` it, and the author starts it from a terminal in the VM. Or a clone in the VM built from source (`sudo bash scripts/linux-deps.sh`, rustup, `. scripts/dev.sh`, as `docs/development.md` says), for runs that change code between tries. The guest is this PC's app (`npm run tauri dev`, or the installed one) in the same room.

**Then, once on GNOME and once on KDE** (sign out, pick the other session), with the author at the VM's screen; ask them to try each, and say what to look for:

| Area | Try | Expect |
|---|---|---|
| Set up | Settings → Drivers → Virtual controllers → Set up | one pkexec prompt; afterwards a session plugs pads (`ls -l /dev/uinput`: the group rule in place) |
| Sharing | Start a session, Start streaming | the desktop's dialog at Start streaming, never when a guest arrives; a window and a screen both; Stop streaming with the dialog open closes it |
| The choice remembered | stream again, and again after restarting the app | no dialog, and the picker says so; Choose again there brings the dialog back for the next stream |
| A window closed, a share stopped | close the shared window; stop from the desktop's indicator | the stream ends, the session goes on |
| The host's keys | the panic key, Accept and Decline, over two Go lives in a row | the desktop's binding dialog the first time; the console shows the desktop's names for them; Accept answers only a request pending 1 s |
| Guests' controllers | the guest takes a seat and plays SuperTuxKart in the VM | the pad moves the kart; `evtest` shows it as an Xbox 360 controller; rumble reaches the guest |
| Sound | the guest listens while SuperTuxKart plays | the game heard; **the request chime never** (the author asks for a seat from the guest side, the host hears the chime, the guest must not); a stream window of the VM's own, watching another host, never in the stream |
| One program | the stream picker's sound: SuperTuxKart, then a browser playing music | only the program picked; the choice remembered for the next stream |
| Replays | if a loopback or EasyEffects is installed | the game heard once, not doubled |
| Notifications | a request, a viewer joining and leaving, with the app's window not in front | a request stays until answered and goes when it is; notes go by themselves; none while the app is in front; none left after quitting the app; no notification sound in the stream |
| Remote play's home PC (part 5) | Settings → Remote play in the VM: a PIN, the Windows app added as a device, remote play on; from Windows, unlock it | the screen-sharing note, no notification-area switch; `systemd-inhibit --list` shows Couch Co-App (`sleep`, then `sleep:idle` once unlocked), or the log says logind refused and the desktop holds it; the VM neither suspends nor blanks its screen past the desktop's own timeouts (shorten them in its settings to try) |
| Its lock screen | lock the VM (Super+L) while Windows is unlocked as its device | the device says the PC is locked within about 2 s, and unlocked again after signing in |
| Streams from afar | from Windows, start a session and a stream, first with no choice remembered (Choose again in the picker at the VM), then after sharing a screen at the VM once; then share a window, close it, and stream from Windows again | refused with the words to share at the PC once; then streams without a dialog; the dialog that comes for the gone window closes after 30 s, and the device says nothing was chosen; on a desktop that never bound the host's keys, a session started from Windows: the shortcuts dialog closes after 30 s, and the console says the keys aren't available |
| Desktop control (M16c-2 part 1) | from Windows, unlocked: a session with the keyboard seat, a screen streamed, desktop control on; type into a text editor, click, scroll, open the app menu with Super; then from a guest (if the seat could reach one: it must not) | keys land at the editor's cursor in the VM's layout (W stays W by position), clicks and the wheel work, the pointer moves (accelerated as the desktop sets); `evtest` lists our `Couch Co-App keyboard` and `mouse` (phys `couch-coapp/<pid>/…`) from desktop control's first grant to the session's end; the console never offers the seat to a guest (no pass entry, the drop refused, Accept disabled with the reason), and Accept in the desktop's shortcut does nothing while Windows has the keyboard (the console's button does) |
| No SysRq (M16c-2) | in desktop control, Print Screen from the device | nothing happens in the VM (no screenshot tool): our keyboard has no SysRq key, and `evtest` on it doesn't list `KEY_SYSRQ`. Guests' blocked combinations (Ctrl+Alt+F3, Ctrl+Alt+Delete) are the router's, checked by its tests and `input-sink` |
| A held key at a kill | the device holds a key (Shift) in desktop control, then `pkill -9 -f -i couch` in the VM | the key isn't stuck in the VM (typing at the VM is lower case); our keyboard gone from `evtest`'s list |
| Start at sign-in | turn it on (the AppImage only), sign out and in; rename the AppImage as a newer version would be, start it once, sign out and in | `~/.config/autostart/couch-co-app.desktop` names the AppImage; the app starts with its window; after the rename, the entry names the new file |
| Teardown | End session; then kill the app mid-game (`pkill -9 -f -i couch`, its stream windows with it) | the pads gone (`evtest` lists none of ours), nothing held in the game; after the kill, a request's notification may stay (only a clean end closes them) |

**Collect** as you go: the app's `desktop.log` in the profile folder (`~/.local/share/CouchCoApp/profiles/default`), `pw-top -b -n 2` and `pw-link -l` while streaming (our node, `couch-coapp-sound-…`, linked to the programs taken), and the guest's stream window stats line.

**Ways to look found on the first run** (2026-11-03/04):
- **Our pad:** its event node by `phys` (`for e in /sys/class/input/event*; …/device/phys` starting `couch-coapp/`), then `timeout 15 evtest /dev/input/eventN` while the guest presses: nothing means our input never reached it (that time, the guest's stream window had no controller: its `viewer.log` in this PC's profile said `Couldn't find mapping for device`, a DualSense asleep). SuperTuxKart logs the pads it sees in `~/.config/supertuxkart/config-0.10/stdout.log`, and drives with the device that picked the kart.
- **Rumble without a game that rumbles:** `sudo apt install -y joystick` once, then `(sleep 1; echo 4; sleep 4; echo 5; sleep 4; echo -1) | timeout 20 fftest /dev/input/eventN`: the strong, then the weak rumble; the other effect kinds are refused (only rumble is offered).
- **A blank window:** whether the page still runs: a notification it sends (a request, with another window in front) still comes. Running, it was WebKit's DMA-BUF renderer (fixed in 0.26.1 for virtual GPUs; try `WEBKIT_DISABLE_DMABUF_RENDERER=1` before the AppImage); not running, a render error.
- **The webview's own messages** (GStreamer's, WebKit's) are in `journalctl --user`, not in `desktop.log`.
- **Inhibitors:** `systemd-inhibit --list`; GNOME's own with `gdbus call --session --dest org.gnome.SessionManager --object-path /org/gnome/SessionManager --method org.gnome.SessionManager.IsInhibited 8` (idle; 4 suspend); KDE's with `…--dest org.freedesktop.PowerManagement --object-path /org/freedesktop/PowerManagement/Inhibit --method org.freedesktop.PowerManagement.Inhibit.HasInhibit`. The lock state: `loginctl show-session $(loginctl show-user <user> -p Display --value) -p LockedHint`.
- **A remembered sharing choice:** the stream picker's Choose again (0.26.1); before it, quit the app and delete the profile's `portal.json`. Neither GNOME nor KDE (its permissions page is for Flatpak apps) can revoke it.
- **The host's keys bound but never pressed** (0.26.1's KDE bug): the console shows keys, yet `dbus-monitor --session "type=signal,interface=org.freedesktop.portal.GlobalShortcuts"` sees no `Activated`. On KDE, read KWin's shortcut service, read-only: `busctl --user call org.kde.kglobalaccel /kglobalaccel org.kde.KGlobalAccel allComponents` (ours: `/component/com_couchcoapp_CouchCoApp`), `getComponent s <app id>`, `getGlobalShortcutsByKey i <Qt key code>` (Ctrl+Alt+Shift+Y is 234881113); and what KDE's portal sends it, `setsid -f timeout 180 dbus-monitor --session "destination=org.kde.kglobalaccel" "type=error" … > ~/kga.log` (detached, or SSH ends it), whose `setShortcutKeys` answers list the keys KWin kept. KDE's portal logs its calls with `systemctl --user set-environment "QT_LOGGING_RULES=xdp-kde*.debug=true"`, then `systemctl --user restart plasma-xdg-desktop-portal-kde` (gone at the next sign-in). **Never call `setShortcutKeys` or `doRegister` with made-up arguments:** a malformed key list crashed KWin, the app with it, and VirtualBox's guest helper then spun until the VM was restarted; `doRegister` alone, then `unregister`, was harmless.
- **A first join to an owner that just started** may time out (15 s, iroh still finding a path): try again before calling it a bug.
