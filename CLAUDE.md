# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Couch Co-App is a Windows-first desktop app for remote "same couch" gaming. A member of a password-protected room streams a game; the others watch, and the host hands control to one of them.

It is a Rust workspace with a Tauri 2 shell (React + TypeScript). Where to read more:
- `docs/architecture.md`: start here. It has the milestone table: what each milestone (M) and polish step (P) did, and what is planned.
- `docs/protocol.md`: the wire format.
- `docs/adr/`: the decisions behind the big choices.
- `docs/development.md` (setting up, running, testing) and `docs/self-hosting.md` (an installer and a relay for your friends): the human guides, which the README links. Keep them in step with the commands here. The README's top is the author's own note; leave it to them.

## Commands

Run from the repo root in PowerShell, after `. .\scripts\dev.ps1`. That script rebuilds PATH so cargo and the FFmpeg/SDL3 DLLs are found, even in a terminal opened before they were installed.

**On Linux** (M16a; Ubuntu 24.04, also in WSL): once, `sudo bash scripts/linux-deps.sh` (the system packages; CI runs it too) and rustup; then in each shell `. scripts/dev.sh`, which chooses Linux's FFmpeg bindings over `.cargo/config.toml`'s Windows default. `fetch-deps`, `stage-dlls`, build, clippy and the tests are the same commands (SDL3 is built from source there, FFmpeg's libraries staged beside the binaries with an `$ORIGIN` rpath). Only `probe`, `host` and `view` exist in `couch-cli` there. In WSL, build in a copy on Linux's own disk, not under `/mnt/c`. `.github/workflows/linux.yml` runs clippy, the tests and the front end's checks on every pull request; keep it green. Nothing streams on Linux yet (M16b).

The desktop app with several profiles: start `npm run tauri dev` (the default profile), then `.\scripts\profiles.ps1` starts alice, bob and carol from the same debug build, logging to `desktop.log` in their profile folders. Each profile runs once: a second launch hands its arguments to the running one and exits before going online, and `Engine::start` also holds `engine.lock` in the profile folder (never run two engines on one identity). `couchco://` invite links open in the default profile. The installer registers the scheme for the installed app (M10a). A debug build registers it for itself (for the current Windows user, which outranks an install for everyone) only with `COUCH_DEV_LINKS=1` set (P5). Without it, a start finding this user's registration pointing at itself removes that registration only (`couch_platform_win::links`; never Tauri's `unregister`, which goes for the installer's machine-wide key first), so an app installed for everyone gets them back. An app installed for just this user writes the same per-user key, so a `COUCH_DEV_LINKS=1` start overwrites it: reinstall that app afterwards. The `app-manual-run` skill covers a manual run: where each profile's logs are, what one PC can't show (games and keyboard and mouse), and what to ask the user to try.

## Architecture in brief

**Main process.** The Tauri app. Its Rust side links `couch-engine`, which owns:
- the iroh endpoint;
- room and session state;
- room sessions (`rooms::sessions`): the one we stream, the one we watch;
- the streaming pipelines, `couch_engine::pipeline` (shared with `couch-cli`): on a host, one capture, an encoder and transport per viewer, one sound capture, and the input task with the seat router and the injectors; on a viewer, `couch-viewer` fed over its pipe. What they need from the machine comes through `pipeline::Backend`, faked in tests.

**Viewer.** `couch-viewer` is a separate child process: SDL3 window, decode, render, audio, input capture, HUD.
- It does no networking. The main process feeds it encoded frames over stdin and reads input and timing from its stdout (`couch_proto::ipc`).
- **Never write to stdout in `couch-viewer`**; `clippy::print_stdout` is denied there. Logs go to stderr.

**Transport.** One iroh QUIC connection per pair of room members, carrying:
- control on a bidirectional stream, framed as `u32 len | u16 type | postcard`;
- video on one unidirectional stream per *epoch* (a keyframe plus the frames that depend on it);
- audio, gamepad, mouse motion and receiver reports as datagrams;
- keyboard and mouse buttons on a reliable stream.

**UI to engine.** One Tauri command, `engine_command(Command) -> Response`, plus one event, `engine-event`, carrying an `Event`. The TypeScript types are generated by ts-rs. A command's reply and the events reach the UI by different channels, in either order, so a room view carries `RoomView::revision` (one counter for every view the engine makes) and the UI keeps the newer of two views of a room (`state/lobby.ts`'s `putRoom` and `refreshRooms`); anything new that stores room views must do the same. The app's own commands (`engine_command`, `restart_app`) are listed in `src-tauri/build.rs` and granted to the main window only (`capabilities/default.json`): the host overlay's window may call none. A new command needs both.

**The front end** (M21; `apps/desktop/src`: `shell/`, `rooms/`, `sessions/`, `settings/` screens; `ui/` the design system on Radix primitives and `styles/tokens.css`; `model/` and `state/` the logic, unit-tested):
- **Tauri only through `platform.ts`** (`platform/tauri.ts` implements it; the overlay's own page listens on its side). The preview's fake (`preview/`) is installed by its own entry, never as a fallback; `npm run build` fails if preview code reaches `dist` (`scripts/check-dist.mjs`).
- **The overlay page stays apart:** no theme tokens, no global styles, no Radix (`overlay/main.tsx`, `overlay.css` scoped to `.overlay`, `page.css` for the transparent window).
- **Nothing jumps:** the shell's regions and dialogs keep their sizes as you move about; state appears in reserved space or below what you use. `npm run shots` checks it (`scripts/shots.config.mjs`'s `STABLE`); add a view there with its moves.
- **Every action on an object is on its button and its right-click** (one `MenuEntry[]` for both, `ui/Menu.tsx`); nothing only in a context menu. The webview's own context menu and browser keys are off (`shell/guards.ts`), but in text fields and `.selectable` text.
- **No key in the webview answers a request or passes a seat** (only the low-level hook does); a request's Accept waits 1 s and is disabled while control is paused (`sessions/HostConsole.tsx`). The patch bay (`sessions/PatchBay.tsx`) hands seats over by dragging with the mouse; its drops send the same commands as the menus, and `dropOn` refuses what the menus refuse (tested).
- **A new screen or state gets a preview scenario** (`preview/scenarios.ts`), so it can be seen and shot without a session.

**Crate boundaries.** Keep these intact:
- `couch-proto`: wire and IPC types. Depends on no other internal crate.
- `couch-media`, `couch-input`, `couch-room`: pure logic, with no OS APIs, FFmpeg or networking.
  - `couch-room` is sans-IO: `(state, input, now) -> effects`, with no clocks, threads or randomness inside (invite tokens and wall-clock seconds come in as arguments). Its Ed25519 and SHA-256 are pure Rust.
- `couch-codec-ffmpeg`: the only crate that links FFmpeg (video).
- `couch-codec-opus`: the only crate that links libopus. FFmpeg's libopus wrapper can't do loss concealment, so audio doesn't go through FFmpeg.
- `couch-platform-win`: the only crate that calls Windows APIs. It compiles to nothing elsewhere (`#![cfg(windows)]`). Before writing unsafe Windows, COM or SDL code, read the `windows-ffi-pitfalls` skill.
  - One exception: `couch-viewer`'s `zero_copy` (M9c) uses `windows`' Direct3D 12 types to hand COM pointers between FFmpeg and wgpu-hal, and reads a resource's description. Keep it to that.
- `couch-platform-linux` (M16, [ADR 0011](docs/adr/0011-linux.md)): the only crate that calls Linux-specific APIs (the `CLOCK_MONOTONIC` clock so far; later D-Bus, evdev, `uinput`, PipeWire). It compiles to nothing elsewhere (`#![cfg(target_os = "linux")]`). The stream window and the engine's backend must read the same clock: the viewer's `now_us` and `Backend::clock` both use it on Linux.
- `couch-gamepad`: physical gamepads through SDL3, for the viewer and the host's own controller. With `couch-viewer`, the only crates that use SDL3. The `sdl3` crate takes the first thread to start SDL as its main thread, so in the engine's process SDL lives only on `couch_gamepad`'s reader thread; never start SDL anywhere else there.
- `couch-engine`: knows nothing about Tauri. `apps/desktop/src-tauri` stays a thin adapter. Its room actor (`rooms.rs`) is the only owner of room state; other tasks report to it over a channel. **Input never goes through the actor**: it runs from the connection through the pipeline's input task to the injectors.
- `couch-net`: each connection has one datagram reader (`datagrams`) and one unidirectional-stream acceptor (`streams`). Subscribe to them by tag or kind; never call `accept_uni` or `read_datagram` yourself, or two readers steal each other's traffic.
- `couch-testkit`: fakes; dev-dependency only.

## Rules that aren't obvious from the code

**Protocol changes**
- Payloads may change in place (nothing is frozen, ADR 0009); prefer a new message type when that's just as simple. Decoders reject trailing bytes.
- **Bump `couch_proto::PROTOCOL_MINOR` with every change to what members exchange** (M10a; permanent since [ADR 0009](docs/adr/0009-source-only-releases.md): there is no public binary release, so the wire format is never frozen). Builds of different revisions refuse each other right after `Hello` (close code `version`), and the app says who needs to update; without the bump, mismatched installs fail in confusing ways.
- **A new wire revision is a minor version** (`couch_proto::REVISIONS` names the version each one arrived in): add its row and `cargo xtask bump minor` in the same PR. The test `a_new_wire_revision_comes_with_a_minor_version` fails otherwise.
- Type ids with bit `0x8000` set are must-understand.

**Versions.** Every PR that changes the app bumps the version once, in that PR: `cargo xtask bump patch` for fixes and small features, `cargo xtask bump minor` for a milestone or a new wire revision. It sets the same version in `Cargo.toml`, `tauri.conf.json`, `apps/desktop/package.json` and our crates in `Cargo.lock`; then say what the version carries in `docs/architecture.md`'s version line ("Installing"). PRs of docs, skills, tests or tooling alone don't bump. If two open PRs both bump, the one merged second takes the next number. So `main` always carries a version not yet handed out, and an installer can be built from it with no PR of its own (the `release-installer` skill).
- Update `docs/protocol.md` with every wire change. The `protocol-change` skill has the full checklist.

**Safety invariants.** Remote input is remote control of someone's PC. Never weaken these:
- Guests default to gamepad only (`Permissions::GUEST_DEFAULT`).
- Keyboard and mouse are injected only while the game window is in the foreground, and only one seat's holder at a time has them (a seat's kind sets its permissions; `SeatRouter::grant` refuses a second).
- The Windows key and its combinations, Alt+Tab, Alt+Esc, Ctrl+Esc, Ctrl+Shift+Esc, Alt+F4 and the gamepad Guide button are never forwarded.
- Every handoff, disconnect and teardown releases held keys and sends `PadState::NEUTRAL`.
- Input with a stale `SeatEpoch` is dropped.
- Remote input reaches `KbmInjector` and `VirtualPad` only through `couch_input::router::SeatRouter`, which enforces all of the above. Its tests are the guard; don't weaken them. After touching input or teardown code, follow the `input-safety-checks` skill.
- **The one exception: desktop control** (M25b, ADR 0010), for the home PC's own unlocked device alone (below, Remote play). A holder granted `Permissions::DESKTOP` has keyboard and mouse without a window in front or the pointer over it, no key blocked, and keeps its keys when the front moves. Guide stays blocked, and every other rule above holds for it. Only `HostSession::set_desktop`'s member gets the bit, only with the keyboard-and-mouse seat; never write `Permissions::all()` for a seat's grant (it includes `DESKTOP`): use `Permissions::ALL_INPUT`.
- Peer data is size-limited: 64 KiB control frames, 16 MiB IPC frames.

**Rooms** ([ADR 0006](docs/adr/0006-rooms-without-a-server.md), `docs/protocol.md` Rooms and Admission)
- **Only the owner lets people in.** The owner signs the roster; members accept connections only from ids on it (iroh authenticates the ids), and only the owner admits newcomers, with an invite it made and the password. Never add a way for a non-owner to admit, or to put anyone on the roster. "The owner" is the chain's tip (M13): the room id binds the founder, and the owner now is the last `to` of the handovers travelling with every policy (`OwnedPolicy`).
- **Handing a room over** (M13, `couch_room::room`; `docs/protocol.md` Handing a room over):
  - the owner offers, the member accepts with a new password of its own (nothing secret travels), then the owner signs the handover after its current version, and that policy is its last; **the offer is void on any new policy or when its connection closes**, and the answer counts only with the same offer id, on the same connection, at the same policy version;
  - **a policy replaces ours only if its chain extends ours** (by body), then by (chain length, version); a diverging chain is never taken; this order comes before any signature check, and only the handovers we don't hold are verified. Never compare policies by version alone: a former owner's later, higher policies under the shorter chain must lose;
  - **every policy we sign goes through `next_policy_version`**, which refuses once we no longer own the room; the new owner signs its first policy at once (`take_over`); the engine takes the password key in or out on `Effect::Ownership`, before the save in the same batch;
  - **a stranger with a made-up chain sees nothing:** being a former member, and a refusal's proof, count only for a chain that is ours or the start of ours, and under the start of ours only for a policy from before the next handover (`Room::compatible`);
  - **an acceptance is for good** (`Room::accepted`): no decline after it, and no leaving, until the room is ours, the owner withdraws, or it signs any newer policy; an offer voided by a dropped connection is withdrawn when its member connects again (`voided`). Leaving meanwhile could leave a room nobody owns;
  - **a relayed policy keeps our own verified copies of the handovers we hold** (`merge_policy`): only the new ones are taken from it, since the ones we skip verifying (same body) could carry planted signatures;
  - no offer while catching up after a restore, nor after Stop waiting until every member has been heard (the mark says `stopped`), nor past 32 handovers (`Room::can_offer`, which the UI follows); a member that merges a newer policy it signed itself and doesn't hold catches up again (as an owner, if the chain makes it one).
- **One writer per fact, signed.** A member signs its own record; only the owner signs the policy (roster, bans), and only the owner handing over signs its handover. Room facts from peers enter only through `couch_room::room`, which checks signatures (`couch_room::signing`). Never accept or act on an unsigned room fact, nor on a peer's claim about someone else (a `banned` close code from a peer proves nothing; the owner's signed policy does). A record counts only within its member's current stay (its `since` matches the roster entry).
- **The roster is shown only to those it concerns.** A refusal carries the owner's policy only for a former member; a stranger gets a bare close. The engine saves room state before sending anything that came from it, so a signed version is never reused after a crash.
- **The admission composition is ours and security-critical** (`couch_net::admission`): SPAKE2, HKDF, HMAC and the TLS exporter. Changing any label, input or order changes what is proven, so update `docs/protocol.md` and ADR 0006 with it. An outside review is optional since ADR 0009, but worth having before encouraging strangers to rely on the app.
- **An opened link never joins by itself.** Any web page can open a `couchco://` link. It only fills in the join screen (through `Engine::open_link`); joining still needs the password and a click.
- **A profile's backup** (M13, `couch_engine::backup`; Settings → Backup) is the identity, the rooms and the settings, sealed with a passphrase (at least 12 characters, trimmed and NFKC-normalized like room passwords; Argon2id, then XChaCha20-Poly1305 with the header as associated data). Keep these:
  - **never an owned room's password key or invites** in it (`Store::backup_contents`): an old backup must never bring back an invite revoked or a password changed since. A restored owner sets a new password before inviting (`RoomView::needs_password`, `EngineError::NeedsPassword`);
  - **restored only into a profile with no rooms**, through the room actor (`Actor::restore_backup`, so nothing is created or joined meanwhile; after it, creating, joining and renaming are refused until the app starts again). `Store::restore` drops whatever a crafted file carries that a backup never does, writes each room's mark (`rooms\*.restored`) before the room, and undoes everything if it fails partway;
  - **a restored room catches up** (`Room::catch_up_first`): it invites and signs nothing (no admission, ban or departure) until it has heard a snapshot from **every** member on its roster (a member's room: from any one), since one away may hold the newest state and a version signed from older state would be ignored by them; then the owner signs the room again at once, `RESTORE_SKIP` (65,536) versions ahead, saved before `Effect::Restore(RestoreMark::Done)` clears the mark: members it never hears from (one let in after the backup while the others were away) may hold what the lost PC signed since, and a policy at +1 would fork them; ahead, they are superseded (whoever only the lost PC knew is dropped). A closing policy and a restored member's last record skip ahead the same way. Only the owner may stop waiting (`Command::StopCatchingUp`, with the UI's warning that a change only the absent hold, a ban among them, can be lost). Leaving is allowed while catching up;
  - **the webview never names the file:** the app opens the save and open dialogs itself (`couch_engine::BackupFiles`, implemented in `src-tauri` with the dialog plugin's Rust API); no window has a `dialog:` permission. A script in the webview could otherwise write the identity anywhere or read any file;
  - the passphrase never reaches the logs, nor the path (`Command::ExportProfile`, `RestoreProfile` and `Response::Backup` print as `..`).
- **Secrets never reach logs.** `InviteToken`, `PasswordKey`, the passwords and invites in `Command`, and the links in `Response` print as `..`; keep it so for anything new. Only the owner stores the password key, never the password.
- After touching rooms, admission, the engine's room actor or `couch_net::control`, follow the `room-security-checks` skill.

**Sessions** (`docs/protocol.md` Sessions)
- **The host is the only writer** of its session's facts, sent straight to each member, never relayed. A member acts on a session message only from that session's host, on the current connection, while the host is on the roster. Never let one member speak for another's session.
- **The seat router alone decides who plays.** `couch_room::session` asks it and mirrors its `Granted`/`Revoked` per seat; never inject or track a holder elsewhere.
- **Seats per viewer: one per controller, decided by the host** (M18). A viewer may hold as many seats with a pad as its stream window has controllers (`ViewerControllers`, the viewer's own word, capped at 4), plus the keyboard-and-mouse seat; `HostSession::keeps` and `HostSession::frees` alone decide whether a grant adds a seat or moves one of the viewer's controllers, counting grants still on their way (`pending`, in the order sent: a router report answers only its own member's grant). **Only the moving controller leaves its seat** (P13): a named controller playing one of the viewer's seats always leaves it, spare controllers or not (moving never adds); a grant beyond the viewer's controllers first revokes as few of its pad seats as keep it within them (normally one), the one the named controller drives first (a request's `controller`, or the host's choice; the viewer's own word on which drives what, `HostSession::set_drivers`); its keyboard-and-mouse seat stays; on the same ordered channel to the router (`HostSession::grant`); keep that order. The host's pass that would have to guess is refused (`SessionError::ChooseController`); an accepted request without a controller frees from the last seat down. The count only chooses add or move: the host still approves every grant, and a count that drops later frees no seat (its pad goes neutral). The session property test must keep reaching a viewer on two pad seats (its ops are weighted for it).
- **A session with no seats is for watching together** (M24): it plugs no pad, hides none of the host's controllers and sets up no hook for the host's keys (`rooms::sessions::session_ready`); every request and pass finds no seat. The input task still runs, with an empty router, so teardown is the same as any session's. Never give such a session a seat or a hook by another path.
- **Only the forwarder decides which of a guest's controllers drives which seat** (`couch_input::forward`): one pad seat, the controller last touched; several, each seat pinned to a controller slot while it is connected. The host may ask for one (P12: `SeatAssigned::controller`, `SeatController`), which the forwarder follows while that controller is connected (a seat it drove swaps); the forwarder's report (`ViewerControllers`) only feeds the host's patch bay, never who holds a seat. The stream window keeps a controller's slot while it is connected (no renumbering) and rumbles and shows by the mapping the forwarder sends (`HeldSeat::controller`); never map them anywhere else. A controller that goes while its guest holds several pad seats gives that seat back (`Forwarder::take_left`, sent as the guest's own give-back); a restarted window (`viewer_replaced`) gives none back.
- **The host on seats** (P2; M23: one seat per controller of theirs). Each of the host's own controllers reaches a pad only through the seat router, as the host's holder with the pad permission only, on that controller's own seat (the input task's local channel, `Inputs::local_input`; `couch-cli host-pad --feed` goes through a router too); never feed one to a pad directly. **Which controller drives which seat is the session's word alone** (`HostSession`'s homes, sent as `Effect::HostSeats` before any claim or grant it concerns, on the same ordered channel): never guess it from order or from the router's holders. A controller's seat comes back to it only when a viewer lets go of it, and only through a claim, which the router grants only if the seat is free, it is one of the host's controllers' seats and control isn't paused: a plain grant there could take a seat a viewer was just passed, and a late claim for a seat a controller left could give the host one no controller drives. Moving a controller revokes its old seat whatever the mirror says (a claim of it may not be reported yet); moved onto another of the host's seats, the two controllers swap. A seat the host takes back or leaves stays empty (only Play here seats a controller again). A host controller that disconnects keeps its seat (the reader reports it neutral). The panic key frees only viewers' seats (`RevokeViewers`, which the router applies from its own holders, never the session's mirror) and doesn't pause the host's controllers. The session property test must keep reaching the host on two seats.
- **Which pads are ours is decided by where they come from** (P9, `couch_platform_win::pad_origin`), never by ids alone: our pads carry a real Xbox 360 controller's ids, as do remappers'. A gamepad's device is found by SDL's path, or for `XInput#N` by the one pad the Xbox driver shows slot N's light on (`xinput_slots`), and must carry SDL's ids; under ViGEmBus it is ours if its serial is in a running host's marker (`virtual_pads`), or in this process's own pads (kept in memory too, M22), while a host is still plugging one, if no serial can be read, or if the markers can't be read; under USB or Bluetooth it is physical. **Unknown counts as ours by ids** (the rule before P9: a pad with our pads' ids is skipped, never listed, never hidden). A host writes its pad's marker before plugging it and adds the serial after; keep that order. A physical controller, or one whose origin can't be told without our pads' ids, can be the host's controller and be hidden by its ids (`pad_origin::may_be_the_hosts`, for the reader and HidHide alike); **another program's virtual pad (a remapper's, M22) only when proven so**, listed as its own kind (`ControllerKind::OtherVirtual`) and hidden by its device alone (`hidhide::hide_virtual`, which checks the origin again); **ours never**, and nothing under a virtual bus is hidden by ids. A remapper's pad stays hidden while it is gone and while it is back but not yet read again, for when the remapper plugs it again under the same device id, and comes off as soon as that device could be something else's (`pipeline::virtual_hiding`: one of the hosts' own by its serial, or plugged in and no longer that follow's, or gone while a host here plugs a pad, looked for every 100 ms while gone); never weaken that. A pad with our ids counts as a remapper's only under ViGEmBus with a serial no host has (`pad_origin::proven_theirs`); a pad proven ours by its serial is never looked at again; a follow re-checks its remapper pad (by serial every second, in full every 5 s, off the hot path otherwise) and drops it if it proves ours; once its pad went, it takes back only its last device or the one remapper pad on offer, never one that was there beside its own (another player's, by number or device; `reader::choose`, with tests); and the follows stop before our pads unplug. A stream window on the same PC skips exactly the hosts' pads and reads the rest, other programs' virtual pads included. Any doubt in finding a pad's device (two pads on one light, a light that can't be read) makes it unknown.
- **A hidden controller is always shown again** (`couch_platform_win::hidhide`): the guard drops after the pads are unplugged, and `restore_stale` (in `Backend::release_left_input`) undoes what a killed host left. Keep both.
- **A pad Windows is still setting up** (P10): the session starts without it, and one task waits for it (`pipeline::host::set_up_pads`, up to `couch_input::PAD_SETUP_LIMIT` or Stop waiting), handing it to the input task when it takes input; its seat drops gamepad input until then. Its marker carries its serial from the moment it is plugged. The input task's end gives the waiting pads up and joins that task after the host's controllers stop being read and before the hiding guard drops: no pad outlives the hiding, and none comes up after the end.
- **Ending releases first:** input, then `SessionEnded` and `SESSION_END`, then encoders and capture, then the pad. A viewer that goes (leaves, closes its window, loses the connection, is banned) is released at once through `SeatRouter::disconnected`.
- **Sessions before streams** (M19, `pipeline::host::HostPipeline`). A session owns the seats, pads, hiding, input task and viewers; streams start and stop inside it (`StreamControl`), and the game exiting or its window going ends only the stream. **While nothing is streamed, viewers' input is held off** (`SeatRouter::hold`, from the session's start): they keep their seats, but nothing of theirs reaches the game, since they can't see. The hold keeps counting their input as heard (no suspension) and keeps mouse totals current (no jump later); the host's own controller is its exception. **Stopping a stream releases first:** the hold (what viewers held is released at once), then each viewer's epoch ends with `STREAM_END` and its encoder closes, then capture and sound. A viewer's video sender lives across streams so its epochs keep counting: the viewer drops older ones. **Starts and stops run one at a time, in the order asked for:** `StreamControl` queues an operation when it is called (not when its future first runs) to the session's one operations task, so the actor must call it synchronously, then spawn the wait. Each start's answer names its request (`OurStream::Starting { request }`); an answer for an older one changes nothing. Stream events (`SourceClosed`, `GameExited`, `CaptureFailed`) carry their stream's number; one from a stream already replaced says nothing, and one arriving while a start is pending is kept until its answer (the starting stream may fail first). Seats are fixed for a session.
- **A seat never survives a connection.** A viewer that reconnects joins again as a new viewer and must be given control again; nothing restores a seat without the host.
- **Every key or button `SendInputInjector` presses is recorded** (`couch_platform_win::held_input`) so a crash can't leave it held. Inject keyboard and mouse only through it, and keep `release_left_input` at the start of anything that hosts.
- **Shortcuts live in one table**, `couch_input::shortcuts`: `SHORTCUTS` holds the defaults, and the user's keys (Settings, saved per profile in `shortcuts.json`) are laid over them by `Shortcuts`, which the viewer (IPC `SHORTCUTS`), the host-keys hook (read at a session's start) and the app all use. Add or change a shortcut there, never as a key constant elsewhere; a new row needs a stable `id`. The user moves keys, never modifiers: only keys in `shortcuts::KEYS` (each with a plain, non-extended scancode; never Esc, Tab, Delete, F4 or the gray navigation keys, which come with fake Shift events), no two rows on one key, and the panic key can't be removed. The host's keys (the panic key, Accept and Decline) go through one low-level hook, `couch_platform_win::host_keys`, which must keep ignoring injected keys: that is what stops a guest holding the keyboard from pressing the panic key or accepting their own request. Never answer requests through `RegisterHotKey` or the webview, which take injected keys too.
- **The host overlay never takes the focus** (M8; its window in `apps/desktop/src/platform/tauri.ts`, what it shows in `overlay/useOverlay.ts`). Keyboard and mouse reach the game only while it is in front, and some games pause without it. The overlay window is created unfocused and unfocusable, closed when empty rather than hidden (showing a hidden window again may activate it), click-through, and excluded from capture. The answer keys answer only a request pending for at least 1 s (`rooms::sessions::ANSWER_AFTER`), so a key meant for one request never answers another that just arrived.
- After touching sessions or the pipelines, follow both the `room-security-checks` and the `input-safety-checks` skills; after touching the host pipeline's video path, the `rate-control-gates` skill too.

**Remote play** (M25, [ADR 0010](docs/adr/0010-playing-your-own-pc-from-afar.md), `docs/protocol.md` Remote play; `couch_engine::remote`, `rooms::remote`). One of the user's own devices (the *operator*) runs a home PC's sessions from afar. Keep these:
- **Trust changes only at the home PC.** Adding or removing a device, the PIN and the switch are commands from its own window; nothing on the wire touches them, and `RemoteOp` never grows a way to. `remote-play.json` stays out of backups.
- **A device sends a PIN only to a PC it accepted** (`remote-hosts.json`), after the user compared codes: an offer alone never makes it send one.
- **The PIN:** only its Argon2id hash is stored, checked off the actor's thread, one check per device at a time (whichever of its connections asks, kept until the check ends), the try counted before it runs; a check started before a PIN change, the panic key, a device's removal or remote play turned off opens nothing (`pin_generation`). Wrong ones wait 1 minute after 5, doubling up to an hour, kept across restarts. Never logged (`Pin`, `Command::SetRemotePin`, `UnlockRemote` print `..`; window titles in `RemoteOp`, `RemoteWindow`, `RemoteStream` too); the device keeps it in memory only.
- **The console's state goes only to operators in the session's room**, and every op (`ListSources` included) refuses while the session (started or starting) is in another room.
- **An operator is per connection:** unlocked on the connection that gave the PIN, from a trusted id, while it is on the roster and remote play is on. Remote messages are never relayed, and a device acts on its PC's only on the connection its offer came on.
- **An operator gets the host's console and nothing else** (`RemoteOp`): each op becomes the home PC's own window command, through the same `Actor::command` and its checks. `StartSession` goes in the operator's room, never with the home PC's controllers; the others act only on a session in that room. Never add room, invite, ban, settings or remote-play ops.
- **The panic key at the home PC locks every operator out** (`RemoteLock { Panic }`, the PIN again), as do a new PIN, removing the device and turning remote play off.
- **Desktop control** (M25b, `RemoteOp::Desktop`, `docs/protocol.md` Desktop control): the session's keyboard-and-mouse seat goes to the unlocked operator with `Permissions::DESKTOP`. Keep these:
  - only from an unlocked operator, in the session's room, watching it, handled in the actor itself (`remote_command_in`), never as one of the home PC's window commands; no other member, seat or the host ever gets the bit (`HostSession::set_desktop`, its property test);
  - **it ends whenever its device stops being an operator:** every path that removes one ends in `announce_hosting`, which checks; keep it so for any new path. Leaving the session, the panic key, the seat passed or taken back, and the end end it too;
  - a member drops `DESKTOP` from any host it doesn't run, unlocked (`rooms::sessions`, `SeatAssigned`);
  - while it lasts, the home PC refuses adding a device, changing the PIN, and accepting, unlocking or running another PC from its own window (the device could click through it; a speed bump, since desktop control is the whole PC), shows the banner in the host overlay whatever its setting, and keeps the pointer on a streamed screen (`KbmInjector::set_bounds`);
  - the stream window grabs the system keys only while its mouse is captured (a click into the picture), and the Free the mouse shortcut gives them back.
- **The unattended PC** (M25c): while remote play is on, the home PC holds a power request keeping the system awake, and the display too while a device is unlocked (`rooms::remote::sync_awake`, called wherever remote play or the operators change: keep it so); while a device is unlocked it looks every 2 s whether Windows is locked (`session_lock::locked`, `RemoteState.locked`). Start at sign-in is the user's own switch, offered only by an installed app's default profile (`EngineOptions::start_at_sign_in`; the HKCU Run value, removed only if it names this exe). The notification area icon is another (`app.json`, `Engine::tray_on`, read by the shell at its Ready event, never before: setup makes the window and the icon then): on, closing the window hides it there and a start at sign-in stays there; off, no icon, closing quits and a start at sign-in opens the window.
- **Bring to front** (`Command::BringToFront`, `RemoteOp::BringToFront`) acts only on the window streamed, never a window named in a command: the op carries none. It taps F24 first (`couch_platform_win::foreground::bring_to_front`), down and up in one `SendInput` call.
- After touching any of it, follow the `room-security-checks` skill, and the `input-safety-checks` skill too when it reaches sessions or input.

**Opening encoders** (M9a)
- **Never call rsmpeg's `AVCodecContext::open` with options.** When the open fails, rsmpeg 0.18 double-frees the dictionary and crashes the process. Open through `couch_codec_ffmpeg::options::OptionSet::open`, which calls `avcodec_open2` itself.
- **Each encoder's options are an ordered list of sets** (`options::option_sets`). The last one is always the settings that worked before; add new sets before it, never replace it. `tests/open.rs` (every encoder, twice, no crash) must keep passing on any machine.

**Frames on the GPU** (M9b on the host, M9c on the viewer, M9d's pacing, M9f's capture; `couch_platform_win::wgc` and `gpu_frames`, `couch_codec_ffmpeg::d3d11` and `d3d12`, `couch-viewer`'s `zero_copy`)
- **NVENC remembers every texture it registers, by address.** So:
  - a pool is replaced only under a new `GpuFrame::source`, and an encoder reading GPU frames reopens when `source` changes (the encode loop in `pipeline/host.rs`; `D3d11Frames::wrap` refuses another pool's frame);
  - an encoder keeps its pool's textures alive until it closes (`GpuTexture::keep_alive`, held by `D3d11Frames`; the codec context drops first);
  - never free, swap or resize a pool's textures in place.
- **When no encoder reads GPU frames** (one couldn't take them, or failed), the stream sets `gpu_input_off`. Since M12a the capture stays on the GPU, paced, and each frame the pacer *sends* is read back once, for every viewer, before the encoders (`pipeline::host::send`): never a frame the pacer drops, and never per viewer. A frame read back is its staging texture's own mapped memory (`gpu_frames::MappedStaging`, unmapped when its last `Bytes` drops; at most 16 per pool, then a memcpy). The capture starts again with frames in memory (`CaptureRequest::in_memory`) only when it can't keep them on the GPU, three read-backs fail in a row (`capture_in_memory`), unpaced, or with `COUCH_HOST_MEMORY_PACING=0`. The mapped staging textures stay made while their pool lives (at most 16, and 256 MB: 8 at 4K); one that can't be made sends frames to the memcpy, never to a failed read-back. `docs/m12a-results.md` has the numbers.
- **The capture is ours** (M9f, `couch_platform_win::wgc`, on Windows.Graphics.Capture directly; `top_windows` and `monitor` list what it can take). Its rules:
  - **two buffers in the frame pool,** so Windows can write the next frame while the GPU still runs our copy of the last. Under Witcher 3 (about 100 fps) one buffer gave about 72 frames a second, two about 107;
  - **in the frame handler, the session's lock comes before `TryGetNextFrame`:** Windows calls it on several threads at once, and a call that waits while holding a frame takes a buffer from Windows;
  - **a closed window is noticed by checking `IsWindow`** every 100 ms: the item's `Closed` event doesn't reliably arrive on a free-threaded pool;
  - **frames under 160x64 are dropped** (a minimized window): one once made NVENC refuse to open, which turned GPU frames off for the whole stream;
  - **no GPU priority:** raising it (Sunshine's calls) delayed Windows' own capture work under a game and halved the gain; measured, dropped.
- **The capture runs faster than the stream only on the GPU** (M9d): a 4 ms interval, each extra frame a GPU copy into the pool, and the capture thread's pacer (`couch_media::pacing`) sends exactly the stream's rate. Windows can't change a running capture's interval, hence the restart above. A capture in memory keeps the one-frame interval: a copy to memory per screen refresh would cost too much; that's why a host whose encoders take frames in memory still captures on the GPU and reads back only the frames sent (M12a). A held (early) frame is dropped if a newer one comes first; how long it waits for one depends on how often frames come (M9e, the largest recent gap, hitches aside):
  - **near the stream's rate:** an interval past its due time. A shorter wait held up a game running a little faster than the stream (61 fps into 60) by up to an interval per frame, for seconds;
  - **a busy source** (over 1.5 times the rate): a gap and a quarter, at the earliest at its due time, so a moment without changes doesn't hold it an interval;
  - **a lone change** (its own gap over two intervals: the first change on a still picture): its due time. Only that frame's own gap counts, and the source's rate ignores such hitches: after one, a game runs as before, and releasing its frames at their due times would make the next ones early.

  The pacer's tests simulate each case; keep them passing. The wait runs on the clock frames arrive by, not their capture timestamps.
- **The capture's device is multithread-protected** (`TexturePool::new`): the capture thread and the encoder threads share it. Keep that for any new user of the device.
- **FFmpeg owns one device reference per encoder** (`GpuTexture::d3d11_device_owned`) and releases it; a wrapped frame owns a `GpuFrame` clone, freed by the buffer's callback. Never hand FFmpeg a borrowed COM pointer as its own. FFmpeg's D3D12VA context releases a device only if it created it, so `d3d12::device_context` installs the `free` callback that does.
- **Measure a performance change against itself turned off** (its switch, e.g. `COUCH_HOST_ZERO_COPY=0`), on the same build: the `performance-checks` skill has the procedure, the known artifacts and the reference numbers. Give each new performance change such a switch, and drop a change that shows no gain (M9d dropped thread and process priorities that way).
- **Only NVENC takes GPU frames** (`gpu_input_encoder(codec)`: `h264_nvenc`, or `hevc_nvenc`). Another encoder gets them from `GpuFrame::cpu()`, copied once per frame. Turning on AMD or Intel GPU input needs testing on their hardware first, and Quick Sync needs NV12 (a conversion shader).
- **HEVC only from an NVIDIA host taking GPU frames** (M12c, `pipeline::host::choose_codec`), to a viewer whose `SessionJoin` says it decodes HEVC. A failed `hevc_nvenc` falls back to H.264 for that viewer alone, never turning GPU frames off for the others. AMD and Intel HEVC needs their hardware first (M12a).
- **Colours follow the stream's declared matrix** (M12c): NVENC converts RGB with BT.601 whatever we ask, and says so; our converter for the other encoders writes BT.709. The decoder puts the declared matrix on every frame (`YuvMatrix`), and the stream window's shader and `capture-test --psnr` use it. Never assume one matrix.
- **HEVC on D3D12VA needs our own frame pool** (`decoder.rs`, `aligned_d3d12_frames`, in `get_format`): FFmpeg's (8.1 to 9.0) is the picture's exact size, and NVIDIA's driver fails to create it for many heights (720, 2160, 900). Ours is aligned to 128, as D3D11VA's; so the viewer's `FrameImporter` copies the picture out of a texture that may be larger. Keep both.
- **On the viewer, FFmpeg's D3D12VA decoder writes into wgpu's own DX12 device's resources** (`FrameImporter`). So:
  - every submit that reads a decoded frame first waits for FFmpeg's fence on the GPU (`add_wait_fence`);
  - the frame goes back to COMMON (`PRESENT` to wgpu) in that submit, the state FFmpeg's next decode expects;
  - a frame is dropped, back to FFmpeg's pool, only after that submit has finished (`on_submitted_work_done`), never sooner;
  - a new wgpu texture is made per frame: never cache one per FFmpeg resource, or wgpu's idea of its state goes stale.
- **Zero-copy decoding is on by default only on NVIDIA** (`COUCH_VIEWER_ZERO_COPY=1` tries other GPUs). Any failure falls back to D3D11VA with copies, logged. Turning it on by default elsewhere needs testing on that hardware.

**Native dependencies and pins**
- FFmpeg and SDL3 are pinned by URL and SHA-256 in `xtask/src/deps.rs` (`WINDOWS_DEPS`; `LINUX_DEPS` holds FFmpeg's Linux build of the same source, M16a). On Linux SDL3 is `sdl3-src` in `Cargo.lock`, built by the `sdl3` crate: keep it at Windows' pinned SDL3 version (`sdl3-sys` isn't `=`-pinned, so a `cargo update` could move it). So are the drivers' official installers the app bundles (`DRIVERS`: ViGEmBus 1.22.0, BSD-3; HidHide 1.5.230, MIT), with their licence texts in `apps/desktop/src-tauri/drivers/`; `stage-dlls` copies them to `target/<profile>/drivers/`, where Settings → Drivers finds them.
- libopus is compiled from source by the `opus` crate, which needs CMake (`doctor` checks). Its CMake build fails past Windows' 260-character path limit, so keep `target/` at a short path.
- The FFmpeg FFI bindings in `crates/couch-codec-ffmpeg/bindings/` are generated and committed. rusty_ffmpeg's build-time bindgen 0.71 produces fieldless structs with libclang 22 or later. Regenerate the bindings whenever the FFmpeg pin changes, one file per system, each on its own system (Windows' and Linux's: C's `long` differs); `xtask`'s test `each_systems_bindings_match_its_pin` fails on both until both are, and `doctor` flags the current system's.
- Exact pins: `iroh` and `sdl3` (`=`). `windows` stays on 0.62 to match wgpu-hal's Direct3D 12 types (`couch-viewer`'s `zero_copy`).
- **vigem-rust is vendored** (`third_party/vigem-rust/`, through `[patch.crates-io]`; P10), with two changes described in its `PATCHED.md`: `ClientBuilder::first_serial`, and keeping a pad Windows is still setting up. Keep both when updating it: pads must take serials from 1 (`couch_platform_win::vigem` connects with `first_serial(1)`), since each serial is a device Windows sets up the first time, and a random one made a fresh PC set one up on most plugs.

**Relays** ([ADR 0007](docs/adr/0007-our-relay-and-release-configuration.md))
- **Which relays run where.**
  - Development: `RelayChoice::N0Public` (iroh's public relays). A release build runs them only when the user picks them in Settings ("for testing"); a saved setting the build can't take falls back to the build's own relay, never to them.
  - Release builds: only the builder's own iroh-relay (`RelayChoice::Custom { urls, token }`); the maintainer's runs at `couchrelay.duckdns.org` for their friends.
  - Tests: `RelayChoice::Disabled`, or `couch_testkit::relay::TestRelay`, an in-process iroh-relay with a token.
- **Our relay admits only clients with its token.** iroh sends it only to relays in our own list; it never goes in invites, member records or logs (`RelayToken` prints `..`).
- **A release build carries the relay's URL and token,** and the invite page's address (`couch_engine::build_config`, `COUCH_BUILD_*` at build time, set by `build-installer.ps1` from `release.toml`, or for the page `-InvitePage`).
- **Settings → Network** (`network.json`): the default, `builtin`, is that relay, or iroh's in a build without one; or `public`; or a URL. `EngineOptions::desktop` reads it, and it applies from the next start (`restart_app`). Plain http relays are allowed on this PC, and at private LAN addresses in development and test builds only.
- **Versions.** The relay server's version follows the iroh pin: bump `RELAY_VERSION` in `deploy/relay/install.sh` with it. `cargo xtask doctor` compares the local relay tool.

**Secrets and release values never go in git.**
- **Where they live:**
  - the relay's token and URL, and the invite page: `release.toml` outside the repository;
  - on the server: `/etc/iroh-relay/token.env`, root-only;
  - any signing key, should one ever be added: a private file or hardware.

  Committed files hold placeholders only (`deploy/release.example.toml`, `deploy/relay/iroh-relay.toml`).
- **Never write a real token, URL with credentials or key into the repository.** The build script refuses a `release.toml` inside it.
- **Builds get them through `COUCH_BUILD_*` for that build only.** The script unsets them afterwards.

**Congestion control lives in the rate controller** (`couch_media::ratecontrol`, ADR 0005). QUIC runs `couch_net::congestion::MediaCongestion`, which deliberately ignores isolated losses. A change to either can collapse the bitrate under random loss or stall recovery after an outage. Run `couch-cli gates` after touching them, or the video transport or encoder bitrate handling (the `rate-control-gates` skill has the procedure); `docs/m1-results.md` has the reference numbers.

**Tests.** `cargo test --workspace` must pass without a GPU, a gamepad driver or internet access, on Windows and on Linux (CI). Tests that need those are opt-in (`#[ignore]` or a `gpu-tests` feature); tests that need Windows are `#[cfg(windows)]`, never removed.
