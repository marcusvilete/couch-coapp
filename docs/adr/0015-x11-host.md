# ADR 0015: The X11 host

**Status:** accepted (2026-11-17), for M28. It extends [ADR 0012](0012-linux-host.md), which made a Linux PC a host on Wayland (KDE and GNOME), to X11 desktops, where that host can't start.

The author's choices (2026-11-17):
- **our own list of windows and screens on X11,** as on Windows: no dialog, and the captured window is the game's;
- **the X server says what is in front,** for guests' keyboard seat: its input focus and its focus events, on every X11 desktop, rather than our KWin script or GNOME extension;
- **in two parts:** M28-1 the capture, the list, controller seats and desktop control; M28-2 guests' keyboard seat, and the host's keys where the desktop has no global-shortcuts portal;
- **tested on Kubuntu 24.04's Plasma X11 session** in the VM (the closest to the Steam Deck's Desktop Mode), then on the Deck.

Settled in M28-1 (0.40.0, [results](../m28-results.md)):
- **What is in front comes from a thread of its own** (`x11::tracker`): the input task asks every 10 ms and x11rb's calls have no time limit, so a look every 16 ms on its own connection, read without waiting, counting for a second. `window_exists` waits up to 300 ms for a new window's first look, and counts it as there if none comes (the capture notices a window that went).
- **A capture only while someone watches,** as on Windows: with no dialog, nothing needs it to start with the stream.
- **A window's sound is everything but this app** (or the program picked), as Wayland's one source; the picker shows the sound choice beside the windows and screens. The engine says whether the picker is the dialog's (`EngineInfo.shares_through_dialog`).
- **MIT-SHM's segment is writable by the server** (it writes the pictures; read-only, every `GetImage` was refused), mapped read-only here; refused anyway, the capture reads over the socket from then on.

Settled in M28-2 (built before the first run on a real X11 desktop, the author's choice, 2026-11-18; the same version):
- **In front** (`x11::tracker`) is the input focus on the game's window or a child, its focus events selected on the tracker's connection (a window not yet selected counts as not in front), no `FocusOut` with mode Grab (another client's grab, detail not Inferior: a game's grab on its own child is the game's) since the last `FocusIn` with mode Ungrab or Normal, and logind's `LockedHint` not set (asked twice a second; the lock screen's own grab says it first). An event with `SendEvent`'s bit counts for nothing. **A grab already held as the window is first watched isn't seen:** the watch starts with the stream, at the host's click in the app (so nobody else held the keyboard then), or from afar. A new connection (the X server restarting) starts over.
- **The pointer over the game** is the deepest window under it being the game's window or a child (its frame's title bar isn't), with no grab elsewhere; a guest's pointer is kept in the game's client area (`KbmInjector::confine`, P18) from the tracker's pointer and the window's area.
- **The host's keys:** the portal first, on X11 too (KDE's works there); where it fails, or nobody answers its dialog, a passive grab of each Ctrl+Alt+Shift chord on the root window (`x11::keys`), four times for Caps Lock and Num Lock, a key another program holds left out of the keys in force, a held key's repeats and sent events dropped.
- **Blocked for guests on a Linux host:** the X server's own Ctrl+Alt with the keypad's plus, minus, divide and multiply (its video modes, breaking or killing a grab where allowed).
- **The GNOME extension isn't offered on X11** (Settings → Drivers): the X server says what the extension would.

Settled by the first run on a real X11 desktop (Plasma 6.6's X11 session in the VM, 2026-11-18):
- **A window is always redirected by its capture** (above): KWin wasn't compositing there, and the window's rectangle on the screen streamed every window over the game.
- **A game switching full screen replaced its window** (SuperTuxKart: its X connection closed and reopened, the new window by the same id), and the stream ended each time: now followed (above). Its controllers were lost by the game itself, which rebuilt its video and never saw them again (its log's `map::at` errors): the game's, not ours.
- **Bring to front** (M25b) works on X11: `_NET_ACTIVE_WINDOW` sent as a taskbar sends it (source 2), restoring a minimized window; on Wayland a stream is never a window, so the button never shows. Its refusal no longer names Windows. It is sent from a thread of its own: the room actor never waits on the X server.

Settled by the review ([results](../m28-results.md#the-review)):
- **A window id is never trusted alone:** the tracker remembers whose each watched window was (`_NET_WM_PID`, else `WM_CLASS`) and watches a window by that id again only if it is the same program's; the capture selects its window's `DestroyNotify`, looks before and after each read, and drops a picture read across a destruction.
- **Grabs:** the focus arriving under another client's grab (`WhileGrabbed`) counts as grabbed; a pointer grab begun over the game (`LeaveNotify` with mode Grab) takes the pointer off it until it ends. One begun while the pointer was elsewhere isn't seen.
- **Nothing waits on the X server where it mustn't:** `window_exists` reads the last look; a lost connection clears every look at once.
- **Only this PC's display** (`:0`, `unix:0`), and a session that isn't the active one counts as locked (logind's `Active`).
- **A refused redirection is tried again** each second.

## Context

A Linux host captures through the screen-sharing portal (ADR 0012). On X11 the portal refuses: a Steam Deck in Desktop Mode (Plasma 6.2.5 on X11) watches and plays, but its streams fail with `Portal request didn't succeed: Other`, since xdg-desktop-portal-kde offers screen sharing only on Wayland. The same holds for Linux Mint (Cinnamon), Xfce and MATE, which are X11 desktops, and for some older NVIDIA setups kept on X11.

X11 is the opposite of Wayland on everything ADR 0012 had to work around:

| Need | Wayland (ADR 0012) | X11 |
|---|---|---|
| Capture | The portal's dialog, frames over PipeWire | Any client reads any window or the screen, silently: MIT-SHM's `GetImage` into shared memory, Composite for a window's own picture |
| Which windows there are | The KWin script or GNOME extension lists them | The window manager's list on the root window (EWMH `_NET_CLIENT_LIST`), each window's title, class and process id (`_NET_WM_PID`) |
| Screens | Whatever the dialog shares | RandR's monitors, each a rectangle of the root window |
| The pointer | The portal's metadata, where offered | XFixes: its shape (`GetCursorImage`) and changes to it; `QueryPointer` for where it is and which window it is over |
| A still window | The portal sends only redraws | Damage says when a window's picture changed |
| Which window is in front | A helper of the desktop's, trusted by its bus name and a token | The X server itself: the input focus (`GetInputFocus`), and focus events on a window, which also say when another client grabs the keyboard (`NotifyGrab`) |
| The host's keys | The global-shortcuts portal | That portal where the desktop has one (KDE on X11: the Deck's host keys worked); else `XGrabKey` |

What X11 doesn't change: guests' pads and keyboard and mouse through `uinput` (the X server reads them through libinput as it reads real devices), the sound from PipeWire, the encoders, notifications, logind.

## Decision

### Which path a session takes

- **X11 only on an X11 session:** `XDG_SESSION_TYPE` is `x11`, or `DISPLAY` is set without `WAYLAND_DISPLAY`. Never on Wayland: there `DISPLAY` is XWayland's, whose root window shows only X clients, so a capture of it would stream a black screen with a few windows on it.
- **Decided once, at start** (a session doesn't change type while the app runs), logged, and shown in Copy diagnostics.
- **The Wayland path stays as it is,** portal and helpers included.

### Capture (M28-1)

- **Through x11rb** (pure Rust over the X protocol, no libxcb; MIT or Apache-2.0, already in the tree through arboard), with its `shm`, `composite`, `xfixes`, `damage` and `randr` extensions, on a connection of the capture's own.
- **A screen:** its RandR rectangle of the root window, through MIT-SHM's `GetImage` into a shared-memory segment, copied out as BGRA. Without MIT-SHM (a remote X server), plain `GetImage`, slower, logged.
- **A window:** its own picture, so other windows over it never show (they could be the host's chat or mail). The capture redirects the window itself (Composite's automatic redirection: the X server keeps drawing it where it was, and undoes it when the capture drops or the process goes) and reads its pixmap (`NameWindowPixmap`, named again each frame), compositor or not, as OBS does. Once redirected, a frame whose picture can't be read is skipped, never taken from the screen. Only where redirecting is refused (another program redirected the window itself): a compositor's pixmap of its frame, else its rectangle on the screen. (The first design read the screen whenever no compositor composited the window; M28's first run, with KWin not compositing in the VM, streamed the windows over the game.)
- **Only the pictures we can read:** a depth of 24 or 32 with the usual masks (`BGRx` in memory on a little-endian machine). Another visual (a 30-bit desktop) fails the capture with a plain reason.
- **The pointer drawn in by us** from XFixes' shape and `QueryPointer`'s position, with `cursor.rs` as for the portal's metadata; a pointer that moves over a still picture makes a new frame of the last.
- **Read at the stream's rate,** changed or not, in M28-1. Damage could say when a still window changed, so nothing unchanged is read: a performance change for later, measured against itself with a switch.
- **The window closing ends the stream,** as on Windows, the session going on (M19), **unless the game shows another:** a window by the same id again, from the same game (its `_NET_WM_PID`, else its window class), within 2 s, is captured on (a game reopening its X connection gets the same ids: SuperTuxKart switching full screen); a new window of the game's process is followed by the pipeline as on Windows (`Backend::game_process`, by `_NET_WM_PID`). Another program's window by that id is never captured.
- **Frames in memory,** read once per frame, never per viewer (M12a's rule); keeping them on the GPU is not part of M28.

### Sources (M28-1)

- **Our own list,** windows and screens, as `Backend::sources` gives on Windows: the windows the window manager lists, ours left out, by title and program; the screens by RandR's names and sizes. No dialog and no restore token.
- **The captured window is the game:** `names_game_window` is false on X11, and Settings never offers Choose again there.
- **Unattended:** a stream started from afar needs no answer (`shares_unattended` is true), so a home PC on X11 streams any source from afar, as on Windows.
- **The sound** stays as on Wayland: every program's but ours, or one program picked. Picking it by the window's process (`AudioKind::Game`) is possible on X11 and left for later.

### Desktop control (M28-1)

- **The pointer is kept on the streamed screen,** as on Windows (`KbmInjector::set_bounds`): X11 tells where the pointer is, so each relative move of the `uinput` mouse is cut to keep it inside, as P18 does for a guest's pointer, never placing it. Every other rule of desktop control stands.

### Guests' keyboard seat (M28-2)

The router's rule stands: keys reach the game only while its window is in front, buttons only while the pointer is over it. On X11 the X server is the source:
- **In front** means the input focus is the game's window or one of its children (`GetInputFocus`, then `FocusIn` and `FocusOut` on it, selected on a connection of our own), and **no other client holds a keyboard grab**: a grab sends the focused window `FocusOut` with mode `NotifyGrab`, and its end `FocusIn` with `NotifyUngrab`. A lock screen, KRunner, an overview, a menu, a run dialog: each grabs the keyboard, so each counts as not in front without knowing the desktop.
- **Forged events count for nothing:** any client can `SendEvent` a focus event to a window; such events carry the `send_event` flag and are dropped. Focus is confirmed by `GetInputFocus` once a change has been seen.
- **The pointer over the game:** `QueryPointer` names the topmost window under the pointer, which must be the game's (or a child), and gives its position for P18's confinement (`couch_input::confine`) in the window's client area.
- **The lock screen** read beside it, as on Wayland (`org.freedesktop.ScreenSaver`, logind's `LockedHint`), though its grab already counts.
- **A quiet source counts for nothing:** the X connection closing (the X server going) ends it at once; nothing is read per input, the router reads the last state.
- **Blocked keys:** those of a Linux host (ADR 0012); the X server's own combinations (Ctrl+Alt+Backspace, Ctrl+Alt+keypad plus and minus) are already among them or are checked in M28-2's plan.
- **The capability:** `keyboard_seat` while `/dev/uinput` is writable, on any X11 desktop; an X server that doesn't answer leaves nothing in front.

### The host's keys (M28-2)

- **The global-shortcuts portal where the desktop has one** (KDE), as on Wayland.
- **Otherwise `XGrabKey`** on the root window, with the same Ctrl+Alt+Shift chords. It hears injected keys as the portal does (`host_keys_hear_injected`), so the guards ADR 0012 set stand: Accept and Decline answer nothing while anyone else has the keyboard, the router refuses guests the chords, the panic key stays on. A key another program already grabbed is reported as lost, and the console offers its own buttons.

### Where the code goes

- **`couch-platform-linux`** gains `x11` (the session type, the connection, the windows and screens), `x11::capture` and, in M28-2, `x11::front` and the keys. It keeps compiling to nothing elsewhere.
- **The engine's Linux backend** asks which path at start and gives each its sources, capture, focus and capabilities. The pipeline doesn't change.
- **No wire change:** guests and devices see a host with the same capabilities as before.

## Consequences

- **A Steam Deck in Desktop Mode hosts,** as do Mint, Xfce and MATE, with no dialog: controller seats and desktop control from M28-1, guests' keyboard seat from M28-2.
- **X11 lets any program of the user's read the screen and every window, and inject keys.** The app adds no new exposure there, but it can't keep anything from other programs either: the same threat model ADR 0012 accepted for programs running as the user.
- **A stream from afar can capture whatever is on the PC**, with no dialog, as on Windows; the home PC's rules (the PIN, trust only at the PC) are what guards it.
- **On X11 the "in front" check is stronger than on Wayland:** a grab is seen, not guessed, so KDE's Overview and GNOME's modal dialogs need no special case there.
- **A window redirected by its capture costs the X server a copy a frame** where nothing composited it before (a full-screen game on a desktop with no compositor, or one that bypasses it): the price of never streaming what lies over the game. Measured on the Deck before anything is done about it.
- **No HDR on X11,** and no fractional scaling to account for.
