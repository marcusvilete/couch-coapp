# P18 results: a guest's pointer kept in the game window on a Linux host

## Why

Three things in one step (**your choice, 2026-11-12**), and what the VM run found in them (below):
1. **The pointer roamed** (your request at M16c-2 part 2's VM run, 2026-11-04). On a Linux host a guest's keys and clicks reached only the named game while it was in front, but the pointer itself was free: over the title bar's buttons, other windows, and into KDE's top-left corner, whose Overview takes the keys unseen.
2. **GNOME's pointer moved at about 2 fps over a still shared window** (the same run): the desktop draws the pointer into the shared picture, and a window sends a new picture only when it redraws.
3. **The invite page's logo** was an old drawing, neither today's icon nor the outline one before it.

No wire change: **version 0.34.1**, which talks to 0.33.0 and 0.34.0.

## The choice

Two ways were open (the handoff's notes): an absolute pointer we place and clamp ourselves, or the relative mouse as it is, its moves clamped against where the desktop says the pointer is. Looking closer:
- **An absolute pointer breaks mouse-look.** KWin passes no relative motion for an absolute device (`processMotionAbsolute`), nor does Mutter, so a game that locks the pointer (any shooter) would get no motion at all, and we can't tell when a game has locked it.
- **Moving the pointer back from the desktop's side** (the KWin script or GNOME extension warping it) would hold the host's own mouse too: Linux has one pointer for every mouse.

So, **your choice: clamped relative moves.** Only our moves are cut, never the pointer.

## What changed

- **The helpers say where the pointer is** (`front/kwin.js`, `front/gnome/extension.js`): each `Front` push carries the pointer's position (`at`) and the active window's client area (`area`: KWin's `clientGeometry`, Mutter's `frame_rect_to_client_rect`). Pushed while the pointer moves: KWin at most every 8 ms (a single-shot timer behind `cursorPosChanged`; KWin 5's poll every 16 ms); GNOME on each move (Mutter's cursor tracker's `position-invalidated`, the signal its own screencasts follow, once per turn of the Shell's loop), its pointer watcher every 16 ms behind it (was 50) should a move go untold; and on a window moving. On GNOME the area is the client area **less what the Shell's panels lie over** (the monitor's work area: a fixed dock, the top bar), unless the window is full screen. `front::pointer(window)` hands them out, only while that window is in front and the helper speaks, with a count of the position's changes.
- **An older GNOME extension confines nothing**, so it no longer counts (`front::gnome`, `EXTENSION_VERSION`, now 4): files of an older version are **Outdated** (Settings → Drivers: "An older version is installed", and **Update**), and while the Shell still runs another version than ours (read from `GetExtensionInfo`) it **needs a log-out**; either way no keyboard seat is offered, and the Start session dialog says where to look (Settings → Drivers).
- **"Over the game" means its client area** (both helpers): clicks and the wheel on its title bar or frame are dropped, as anywhere else not the game (the router's `pointer_inside`).
- **The clamp** (`couch_input::confine::Confiner`, pure): each relative move is cut, per axis, to the room between the reported position and the area's edge it goes towards, divided by the worst acceleration a desktop applies (`WORST_ACCELERATION`, 4: libinput's adaptive profile at its highest speed), less what may not be in the report yet: everything sent that way since it came, and what was sent in the 20 ms before it (`IN_FLIGHT`: the desktop read the position, then told us), those only while they're 20 ms old at most (had they moved the pointer, a newer position would have come by then). So the pointer moves freely inside, slows only near an edge until the next report, and never crosses it, whatever the acceleration. A pointer outside the area (the host's own mouse put it there) is only let back in.
- **A locked pointer** (a game in mouse-look): our moves stop moving it. Once at least 16 units went unanswered for 200 ms (`LOCKED_MOTION`, `LOCKED_AFTER`), moves pass whole until the position changes again, which a game letting the pointer go does. Moves cut to nothing (pressed against an edge) never count as unanswered.
- **Wired in** through `KbmInjector::confine(window)`, which the input task sets beside desktop control's bounds (`Inputs::sync_confined`): the named game window for any keyboard-and-mouse holder, **never for desktop control**, nothing while no window is known. Only the Linux injector (`couch_platform_linux::kbm`) does anything with it; Windows' does nothing.
- **The pointer drawn by us** (`couch_platform_linux::cursor`, `screencast`): the capture asks the portal for the cursor as metadata where offered (`CursorMode::Metadata`, else Embedded as before) and for `SPA_META_Cursor` room for a shape of up to 1,024 pixels each way (OBS's range: each desktop offers one fixed size, KWin's for 256 pixels, Mutter's for 384, and it must fall inside ours), drawing shapes up to 384; each buffer's pointer position (less the crop region's corner) and new shape are taken in, the pointer is blended into each picture, and a buffer with only the pointer in it makes a new frame of the last, what the pointer covered put back and the pointer drawn where it is. Where the desktop says the shape's header and pixels are is checked before each is read (aligned, past the cursor's own, within the most room asked for); the room agreed may be less, and within it the compositor is trusted, as it is for the picture (the review's finding, below).
- **GNOME's Alt+F7, Alt+F8 and Alt+F10** (moving and resizing the window by the keyboard, which takes the keys without the front changing, and maximizing it) are refused to guests on a Linux host, beside Ctrl+Alt+T and the rest (`filter::desktop_key`).
- **The stream window takes the mouse only after a click into the picture** (`couch-viewer`'s `input.rs`; **your choice, 2026-11-12**): before, it took it as soon as the window had the focus while you held the keyboard seat, so the bar and its Give back were out of reach without Ctrl+Alt+Shift+M. Now at the start, and after the focus went elsewhere, the pointer stays free until a click into the picture (that click isn't sent); Ctrl+Alt+Shift+M still frees it.
- **The invite page's logo** is the app's icon (`deploy/invite-page/j/icon.svg`, a copy of `icon.svg` with its own first line; CLAUDE.md's icon row says so); and its note for those without the app says it is for Windows and Linux (an AppImage there), no longer Windows alone.

## Found while checking

- **After the merge: drawing with a Linux host never reached the host** (older than P18, since M27d; fixed in 0.34.2). In the VM, guests on Windows saw each other's drawings through the Linux host, but its own stream window showed none of them, and what the host drew there reached nobody; a Windows host worked with the same guests. The host was named the board's author (`HostSession::set_me`) only where it draws over the game (M27b, Windows), yet its own stream window (M27d) opens on every system and draws as that author: unnamed, the session sent it nothing and took none of its batches, silently. Now the host is named in every session. The scenario `a_host_that_cant_draw_over_the_game_draws_in_its_own_window` failed without the fix (the window never heard B's) and passes with it; M27d's own scenario turned the board over the game on, so it never saw this. Drawing with a Linux host had never been tried in a VM run. In the VM with a 0.34.2 test build (KDE, guests your Windows profiles on 0.34.1), the guests' drawings appear in the Linux host's own window and the host's reach every guest, you found.

- **The VM run found six things, each fixed here:**
  - **No pointer at all in GNOME's shared picture.** Mutter offers the cursor's metadata at one fixed size (room for 384 pixels each way, 589,872 bytes, read from its port with `pw-dump`), outside our range (up to 256): nothing was agreed, and the desktop, asked for metadata, drew no pointer either. KWin's 256 fit. Now up to 1,024, as OBS asks.
  - **An extension of an older version was taken as ready.** The files were the new ones, but GNOME still ran version 1 (read at log-in), which says nothing of the pointer: the keyboard seat was offered and nothing confined. Now the version GNOME runs must be ours; and Settings → Drivers said **Install** and "Not installed" for an older version, now **Update**.
  - **Fast moves got out.** Each new position started the count again, but a report is read a moment before it comes, so moves on their way got the edge's room a second time (the new test reproduces it: out by 117 pixels). Moves sent in the 50 ms before a report then counted, which made the pointer stop and go near edges; worse, when those used up the room nothing more went, so no newer position came and the pointer **stayed short of the edge for as long as the guest kept moving** (only stopping and starting again freed it). Now they count only while 20 ms old at most, and GNOME's extension reports on every move (**your choice**, over a shorter wait alone).
  - **Ubuntu's dock lay over the game's window** (fixed on the left, over the window's first 10 pixels): the pointer, inside the window's area, hovered the dock's icons, and the shared picture's pointer vanished there (GNOME shows none while the pointer is over something else). The area is now cut to the work area.
  - **Alt+F7 and Alt+F8 moved and resized the window from the guest's keyboard**, which takes the keys without the front changing (**your choice** to refuse them, with Alt+F10).
  - **The stream window took the mouse at once**, so its bar was out of reach (above).
- **Windows that draw their own title bar keep it inside their area.** GNOME's Text Editor (a GTK header bar) and Kate run natively on Wayland (Qt's decorations, a shadow about 10 pixels wide inside the window's geometry) have their title bar's buttons and resize margins inside the rectangle the desktop gives, and no desktop interface says where an app's own decorations end. So a guest can still reach those: the pointer stops 3 pixels inside the rectangle, in Kate's shadow. Confinement is as tight as the rectangle: exact for windows the desktop decorates (KDE's, X11 apps on GNOME) and for full screen, which games mostly are. Known, left as it is.
- **What a VM run needs to know:** VirtualBox's mouse integration moves the VM's pointer wherever this PC's mouse is over its window, absolutely, the host's own mouse, never confined: turn it off (Input → Mouse Integration) while trying a guest's pointer. Since the stream window no longer takes the mouse until a click, this PC's mouse is free to wander there. And `npm run tauri dev` restarts the guest's app whenever a crate it builds is edited.
- **C: filled up** mid-run (`target\debug` had grown to 183 GB: 80 GB of incremental caches, 98 GB of artifacts from older versions), stopping WSL. You agreed to `cargo clean --profile dev`. Afterwards WSL's own incremental cache, written while the disk was full, crashed rustc (`rustc_query_impl/src/incremental.rs`) until it was removed; and once `couch-media`'s test harness couldn't read random data at its start (`failed to fill whole buffer`), passing when run again. ## The review

A fresh agent went over the whole branch against main. Nothing weakened the input rules (confinement never set for desktop control, the host's own mouse never cut); what it found, each checked against the code:
- **A false "locked" let every move through** (medium-high). The lock counted motion in all four directions, so jitter that moved the pointer less than a pixel reached it; a busy Shell, saying nothing for 200 ms, looked the same; and on KDE an area reaching past the screen's edge left room the pointer can't use. Fixed: the lock counts net motion along each axis, and only once the helper has spoken since our moves had time to show (a quiet desktop proves nothing); KWin's area is cut to its screen's usable area as GNOME's is (which also keeps a Plasma panel over the game out). Working it out found one more: jitter used the room up both ways and could hold the pointer still for good, so the same position told again (each helper's heartbeat, every second at least) now retires the moves it must include. Tests `a_quiet_desktop_is_never_a_lock`, `jitter_is_never_a_lock_nor_holds_the_pointer`.
- **When a position came was the first move after it, not its arrival** (medium): now the time `front` heard it.
- **The cursor's bitmap header was read before its offset was checked** (low; the compositor is trusted with the picture as it is): now its offset and alignment are checked first, and the docs say what is checked: within the most room asked for, not the room agreed, which `Buffer` doesn't give.
- **No report while the game counts as in front let the whole move through** (low): now nothing goes (`without_a_report_nothing_goes`).
- **The extension's version and code could drift apart** (low): a test pins a hash of `extension.js` to its version (`the_extensions_version_moves_with_its_code`).
- **Coming back to the stream window took two clicks** (low): SDL drops the click that focuses a window, so `SDL_MOUSE_FOCUS_CLICKTHROUGH` is on; that click only captures, as any first click (and off while drawing: below).
- **A second, fresh review** of these fixes (the first's top finding was medium-high) found nothing high, and:
  - **a lock could still rest on one push** read before our moves landed and heard late (our process busy), the new position right behind it: moves would then pass whole until it came. Now a lock needs the same position told at least 100 ms after the first unanswered move (`STILL_AFTER`) and nothing newer for 20 ms; and the same position told again retires only what was sent 100 ms before it (`the_same_position_told_right_after_moves_keeps_them`, `a_late_push_of_the_old_position_is_no_lock`; the lock test now fails on the rule before);
  - **a real mouse-look lock waited for the helpers' one-second heartbeat** (they push only changes between beats, and a locked pointer doesn't change), holding the camera to a quarter of the room meanwhile: both helpers now tell what is in front and where the pointer is every 250 ms (the window list still each second), so a lock is found in about 0.35 s. The GNOME extension is version 5 for it;
  - **in drawing mode the click that focuses the window would draw** (a dot, or a selection lost, sent to everyone): the click-through hint is off while drawing;
  - **a report gone a moment forgot what was on its way**: kept now (`a_report_gone_a_moment_forgets_nothing`).
  - Not done, to try: whether a desktop scaled to 200% multiplies the moves past `WORST_ACCELERATION` (Mutter in its physical layout may scale relative motion by the monitor's scale); the area is one monitor's usable part, so a game window across two loses the other's part (never an escape).
- Left as they are, noted: a pointer-only buffer copies the whole last frame (at 4K about 33 MB a move; only over a still window, at most at its refresh rate); the GNOME extension pushes on every move of the host's own mouse while a session watches; a newer extension installed by a newer AppImage shows as Outdated to an older one.
