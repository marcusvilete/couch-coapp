# Architecture

Couch Co-App lets friends play a game "on the same couch" over the internet. One member of a password-protected room streams a game; the others watch, and the host hands control to one of them.

This document describes how the pieces fit together. The wire format is in [protocol.md](protocol.md); the reasons behind the big choices are in [adr/](adr/).

## Processes

```
Host machine                                    Viewer machine
+-----------------------------------+           +-----------------------------------+
| Tauri app (main process)          |           | Tauri app (main process)          |
|   React UI (webview)              |           |   React UI (webview)              |
|   engine: rooms, sessions         |<- iroh -->|   engine: rooms, sessions         |
|   capture -> encode (per viewer)  |   QUIC    |          | stdin/stdout pipe      |
|   seat router -> ViGEm, SendInput |           | couch-viewer (child process)      |
+-----------------------------------+           |   decode -> render, audio out     |
                                                |   keyboard, mouse, gamepad, HUD   |
                                                +-----------------------------------+
```

- **Main process.** The Tauri app. Its webview shows the lobby and room UI; its Rust side links the engine, which owns the iroh endpoint, room and session state, and (on a host) capture, encoding and input injection.
- **Viewer process.** `couch-viewer`, started by the main process when its user joins a session. It owns a native SDL3 window, decodes and renders video, plays audio, captures local input and draws the in-stream HUD.
  - It does no networking. The main process forwards encoded frames over the viewer's stdin and reads input events and timing from its stdout (`couch_proto::ipc`).
  - Logs go to stderr. If the main process dies, the viewer sees end-of-file and exits.
- **Why the stream isn't in the webview.** Browser jitter buffers add about 100 ms. Webviews can't grab the keyboard or read gamepads reliably. Linux's WebKitGTK has no WebRTC. See [ADR 0002](adr/0002-separate-viewer-process.md).

Rules that keep this layering useful:

- **Sans-IO state machines.** `couch-room` transitions take `(state, input, now)` and return effects. No sockets, threads or clocks inside, so they are deterministic and property-testable.
- **One crate per native boundary.** Only `couch-codec-ffmpeg` links FFmpeg, only `couch-codec-opus` links libopus, and only `couch-platform-*` calls OS APIs. Logic crates therefore build and test anywhere, without LLVM, FFmpeg, a GPU or drivers.
- **The engine knows nothing about Tauri.** The UI talks to it through one Tauri command (`engine_command`, taking a `Command`) and one event (`engine-event`, carrying an `Event`). TypeScript types are generated by ts-rs into `apps/desktop/src/bindings/` (`cargo test -p couch-engine`).

## Data paths

**Host, per frame.**
1. A `Capturer` (Windows.Graphics.Capture, used directly since M9f: `couch_platform_win::wgc`, with a frame pool of two buffers) delivers a BGRA frame stamped with QPC time. Since M9b it stays on the GPU: copied, GPU to GPU, into a texture pool on the capture's D3D11 device (`couch_platform_win::gpu_frames`) and handed on as a `GpuFrame`, which every viewer's mailbox shares. Since M9d the capture runs faster than the stream (up to every 4 ms, frames on the GPU only), and the capture thread's pacer (`couch_media::pacing`) sends frames at exactly the stream's rate: Windows composes only on the screen's refresh, so a capture limited to one frame per interval lost frames on screens whose refresh isn't a multiple of the rate. An early frame is held for its due time; how long it then waits for a newer one depends on how often frames come (M9e).
2. Each viewer's `VideoEncoder` (through FFmpeg: NVIDIA's NVENC first, then AMD's AMF, Intel's Quick Sync or Windows' Media Foundation; one encoder per viewer) produces an H.264 access unit, or since M12c an HEVC one: `hevc_nvenc` for a viewer whose GPU decodes HEVC, when the host is NVIDIA and takes GPU frames (`pipeline::host::choose_codec`; a failed HEVC encoder falls back to H.264 for that viewer alone). NVENC reads the texture itself (`AV_PIX_FMT_D3D11` frames on the capture's device). When the encoder can't read them (another vendor's, or NVENC on another GPU than the capture's), the capture starts again with frames in memory for the rest of the stream, as before M9b, at Windows' one-frame interval (each frame in memory costs a copy). An encoder reading GPU frames reopens when the pool changes (a new device or size), and keeps its pool's textures alive until it closes.
3. That viewer's `VideoSender` writes it to the current epoch stream.
4. A rate controller per viewer adjusts its encoder's bitrate from the transport-neutral `FeedbackSnapshot`.

**Viewer, per frame.**
1. The main process receives the frame on the epoch stream.
2. It forwards the frame to `couch-viewer` over stdin.
3. The viewer decodes it and presents it immediately; there is no jitter buffer for video. Since M9c the frame stays on the GPU: FFmpeg's D3D12VA decoder runs on wgpu's own DX12 device, and the render thread copies the decoded NV12 planes, GPU to GPU, into the textures it draws (`couch-viewer`'s `zero_copy`), after waiting on the GPU for the decoder's fence. Where that can't run (not NVIDIA by default, or `COUCH_VIEWER_ZERO_COPY=0`), D3D11VA decodes and the frame is copied through memory, as before. If D3D12 decoding fails once running (it can't start on the stream, keeps failing, or its frames can't be brought in), the stream window switches to D3D11VA and copies at the next keyframe, still presenting through DX12. Each frame names its codec (M12c), and the decoder reopens for another at a keyframe. The shader converts with the matrix the stream declares (`YuvMatrix`): NVENC's BT.601, or BT.709 from our converter for the other encoders. For HEVC on D3D12VA, the decoder's frame pool is ours, aligned to 128 lines: FFmpeg's own is the picture's exact size, which NVIDIA's driver refuses for many heights (720 and 2160 among them), so the importer copies the picture out of a larger texture. The shader scales the picture to the window with Catmull-Rom on luma, bilinear on chroma (P8; `COUCH_VIEWER_SCALER=bilinear` for bilinear on both).
4. Decode and present times go back over stdout and become receiver reports.

**Audio, host to viewer** ([protocol.md](protocol.md#audio)).
1. WASAPI process loopback captures the game's process and its children (`couch_platform_win::audio`). For a monitor source it takes everything except our own processes. Packets come every 10 ms, stamped with QPC time.
2. `couch_media::audio::Framer` cuts them into 10 ms frames; Opus encodes each at 96 kbit/s (`couch-codec-opus`); each packet goes as one datagram.
3. The viewer's main process forwards packets over stdin. In `couch-viewer`, an adaptive jitter buffer (`couch_media::audio::JitterBuffer`, 10 to 40 ms) feeds SDL's audio thread, which decodes or conceals a 10 ms frame at a time.
4. SDL plays them on the default device. The buffer's playback ratio (at most 2% fast or slow) drives SDL's resampler, absorbing the drift between the two machines' audio clocks.

**Input, viewer to host** ([protocol.md](protocol.md#input)).
1. SDL3 captures local input in the viewer: keys as scancodes, which are HID usages; the mouse in relative mode; gamepads, also in the background.
2. It travels to the main process over stdout. There `couch_input::forward` adds the seat and its epoch, keeps the running mouse totals and sends the heartbeat.
3. Keys and buttons go over iroh on the input stream; pad state and mouse motion go as datagrams.
4. On the host, `couch_input::router` lets input through only from the seat's holder, with the current seat epoch and permissions, and keyboard and mouse only while the game is in front.
5. Accepted input drives the ViGEm pad or `SendInput`. Rumble goes back as a datagram.

The host keeps frames on the GPU since M9b (`EncoderInput::Gpu`), and the viewer since M9c (`DecodedFrame::Gpu`).

## Measuring latency

All timestamps are QPC microseconds, so on one machine the host's and the viewer's clocks are the same clock.

- **The latency clock.** `couch-viewer --clock X Y` opens a small window that paints the QPC time every frame:
  - as a barcode of 66 cells, 16 px each: a white and a black sync cell, then 48 bits of the value and a CRC-16/CCITT-FALSE;
  - and as digits, for people.
- **Clock to present.** The host captures that window. The viewer reads the barcode out of each decoded frame (`couch_media::barcode`) and compares it with the QPC time at present. This is the end-to-end number for gate G1. It includes the clock's own render and the compositor before capture, about 9 ms.
- **On screen.** `latency-probe --screen` captures the whole monitor, where the clock and the viewer's copy of it sit side by side, and reads both barcodes (gate G1b). Only values from the last 2 s count, which rejects false matches.
- **Capture to present** starts at the frame's capture time.
  - **Windows' timestamp runs ahead of delivery,** roughly to when the frame will be on screen. For a window whose own frames queue up, it was later than our decode had finished, so the figure read 0.
  - **Since P5,** the capture time is the earlier of Windows' timestamp and the frame's delivery (`couch_platform_win::capture`). It is an honest lower bound, but excludes the compositor before capture.
  - **The barcode figure (clock to present) is the end-to-end one.** Capture-to-present numbers in results before P5 read a few ms low.
- **Impaired networks** come from `couch_net::netem`, a test-only iroh transport over loopback UDP. It adds delay, random loss, a rate limit with a drop-tail queue, and scheduled blackouts or rate changes.
  - iroh can't switch off its own multipath and NAT traversal, so a tool like clumsy would see traffic on paths it doesn't impair.
  - A blackout set on the host's side cuts both directions.
- **Rate-control traces.** `host --rc-trace file.csv` (or `latency-probe --rc-trace`) writes every controller tick. `view --timings-csv` writes every presented frame. Both use QPC time, so the two files line up. With `--netem`, the host's trace also records the time since the netem link started (`netem_us`), which places scheduled blackouts and rate changes exactly.
- **Gates.** `couch-cli gates` runs G1 and G3 to G5 through `latency-probe` and judges them from those traces. The `rate-control-gates` skill (`.claude/skills/`) has the procedure and how to read a failure.
- **Audio.** The clock window also clicks twice a second. `latency-probe --audio` loopback-captures the clock and the viewer and pairs up the clicks (click to playback). The viewer also reports, from packet timestamps, how long audio takes from host capture to being handed to the audio device; that is gate A1. See [m3-results.md](m3-results.md) for why the two differ by Windows' own playback path.

## Connectivity

- **One transport.** Every pair of room members shares one iroh (QUIC) connection. It carries control, video, audio and input ([ADR 0001](adr/0001-iroh-for-all-traffic.md)).
- **Connection setup.** iroh hole-punches a direct path when it can, which is about 9 pairs in 10, and falls back to a relay server otherwise.
- **Congestion control.** The per-viewer rate controller does it. It is delay-based, much like WebRTC's GCC. QUIC runs our `MediaCongestion` controller, which ignores isolated losses and probes quickly after an outage ([ADR 0005](adr/0005-media-congestion-control.md)). Stock Cubic and BBR v3 cut the bitrate to a tenth under 1% random loss.
- **Relays** (`couch_net::endpoint::RelayChoice`):
  - Development: iroh's public relays (`N0Public`), whose terms cover hobby use only.
  - Release builds: only the builder's own `iroh-relay` on a small VPS, with no third-party address lookup (`Custom`) (M7, [ADR 0007](adr/0007-our-relay-and-release-configuration.md); there are no official builds or relay, [ADR 0009](adr/0009-source-only-releases.md)).
    - **The token.** The relay admits only clients with its token (`access.shared_token`). iroh sends the token only to the relays in our own list, never to another member's.
    - **Built in.** A release build carries the relay's URL and token (`couch_engine::build_config`, from the private `release.toml` that `build-installer.ps1` reads). Settings → Network's default choice (`RelaySetting::Builtin`) uses it, and is iroh's public relays in a build without one.
    - **The deploy kit** is in `deploy/relay/`. `scripts\relay.ps1` runs the same server on this PC.
  - Tests: no relays (`Disabled`), or an in-process `iroh-relay` with a token (`couch_testkit::relay`).
- **Joining a room.** Only the room's owner admits newcomers. An invite link carries the room's owner and nonce (which make its id), the invite's own token and the owner's relay (or addresses on a LAN). The newcomer and the owner check the room password with SPAKE2; it never leaves either machine.

## Rooms

([protocol.md](protocol.md#rooms), [ADR 0006](adr/0006-rooms-without-a-server.md))

- **Identity.** Each profile has one Ed25519 key, which is both its iroh endpoint id and its member id. It lives in `identity.key` in the profile folder, sealed with DPAPI.
- **Who is in.** The owner (the creator) signs the roster. Only the owner admits newcomers, with an invite it made and the password, and only the owner removes anyone: a ban, a departure, or closing the room is a new roster.
- **The mesh.** Every member connects to every other member of a room. Members accept a connection only from an id on the owner's roster; the dialer shows its copy first, so a member who missed a join catches up. Members dial everyone they know; crossed dials settle on the one the lower id made. They reconnect after restarts without the owner.
- **State.** `couch_room::room::Room` holds one room as one member sees it: the owner's signed policy, signed member records, the connections, and, for the owner, its invites. It is sans-IO. `couch-engine`'s room actor runs one per room. It owns the connections, carries out the machine's effects (dial, send, close, save) and turns its status into the UI's `RoomView`.
- **Remembered rooms.** One file per room in the profile folder (`rooms/<id>.room`), sealed with DPAPI: the saved state and, for rooms we own, the invites and the password key (never the password). At start every remembered room dials all its members; a room with nobody online waits for others to dial in.
- **Gate and limits.** The endpoint's post-handshake hook refuses ids in backoff before any of our protocol runs. The owner checks the rest when a newcomer names its room and invite.

## Sessions and control

([protocol.md](protocol.md#sessions))

- **Where they live.** A session rides on its room's connections: the roster already decides who may watch. The host is the only writer of its session's facts and sends them straight to each member.
- **Ownership.** The host owns the session's state: viewers, requests, who holds each seat, the control pause (`couch_room::session`). Who holds a seat is decided by the seat router alone (`couch_input::router`); the session mirrors it.
- **Seats** (P1; one setup since M19). The session's input setup (`InputSetup`, chosen when it starts and fixed for it; the app remembers the last one) gives the seats: 0 to 4 controller seats, each its own virtual pad, and keyboard and mouse as a seat of their own or with Controller 1 (one player on both, single player's old "both").

  The seat's kind sets its holder's permissions. **Seats per viewer** (M18): one per controller the viewer's stream window has (`ViewerControllers`), plus the keyboard-and-mouse seat; a grant beyond that moves the viewer, revoking its other pad seats first (`HostSession::keeps`). The forwarder pins each of the guest's pad seats to one of their controllers (one pad seat: the controller last touched), and tells the stream window, which rumbles and shows by it; a controller that disconnects gives its seat back, and the others stay put (`couch_input::forward`). Only one holder at a time has keyboard and mouse (the router refuses a second).
- **Sessions before streams** (M19). Starting a session plugs in the pads and hides the host's controller before any game runs; streams start and stop inside it (`pipeline::host::HostPipeline`, each stream its own source, frame rate, rates, capture and sound). While nothing is streamed, the seat router holds viewers' input off (`SeatRouter::hold`): their seats stay, their input reaches nothing, the host's own controller plays on.
- **The host on a seat** (P2; M23: on several, one per controller). In P1's co-op run, the game gave player 1 to the host's own DualSense, so a guest's virtual pad got no player. So the host can now play seats too: the session's "Your controllers" choice.
  - **Reading them.** The engine reads those controllers with SDL3 on a thread of its own (`couch_gamepad::host_pads`; the `sdl3` crate allows one SDL thread per process, and nothing else in the app uses SDL). Its states enter the input task and go through the seat router as the host's own holder, with the pad permission only.
  - **Hiding it.** HidHide hides the controller from every other program for the whole session (`couch_platform_win::hidhide`): every node of it, by container id, never a virtual pad's (P9), and our exe goes on its whitelist. A remapper's pad chosen as the host's controller (M22) is hidden by its device alone, and kept hidden while the remapper plugs it again (`pipeline::virtual_hiding`). HidHide refuses only new opens, so a game or Steam that had the controller open keeps it until it is reconnected; since M19 the session starts before the game, so a game started afterwards never has it. For a Steam game, Steam Input must be off for it: otherwise Steam keeps a player for the hidden controller and one seat gets none (seen in Fling to the Finish).
  - **Showing it again.** With HidHide 1.5.230 (the latest release) the entries go on its persistent blacklist, and a marker file records exactly what we changed: stopping undoes it after the pads are unplugged, and the next start of the app or of `couch-cli host` undoes what a killed host left. HidHide's newer session blacklist, which the driver clears when our process exits, is used when present.
  - **The seats** (M23: several controllers, one seat each). Each chosen controller starts on its own seat with a pad, in order; the session alone says which controller drives which (`HostSession`'s homes, told to the input task before any claim). A controller's seat comes back to it when a viewer lets go of it (a *claim*, granted only if the seat is still free, is one of the host's controllers' seats, and control isn't paused). Play here moves one controller (its old seat goes free), or swaps two of the host's. A seat the host takes back, or leaves, stays empty until they choose Play here; a host controller that disconnects keeps its seat. The panic key frees the viewers' seats only, and doesn't pause the host.
  - **Without it** (no HidHide, no controller, or the host's choice) the host plays outside the seats, as in P1: on a single seat while nobody holds it, otherwise beside them.
- **Handoff.** Passing a seat changes its holder and increments its epoch, releasing first. The virtual pads stay plugged in for the whole session, so the game never sees a controller disconnect.
- **Requests.** Viewers ask for a seat; the host accepts or declines, passes a seat without a request, or takes one or all back. The panic key takes everything back and pauses control.
- **The game's focus.** The host's input task notices the streamed window leaving the front and tells the viewers (`GameFocus`), whose stream window says why input may not work.
- **Disconnects.** If a viewer leaves, closes its window, loses its connection or is banned, everything it held is released at once.
- **In the engine.** The room actor runs the session protocol (`rooms::sessions`). The media and input run in `couch_engine::pipeline`: `HostStream` (one capture, an encoder per viewer, one sound capture, one input task) and `Watch` (the viewer process). **Input never goes through the actor**: it flows from the connection to the input task's seat router to the injectors.
- **On screen.** The app's stage shows a card per live session (Watch, ask, stop watching) and, for the host, a panel with the viewers, the requests and the pause; the taskbar flashes on a request. The viewer's HUD shows the session and takes clicks on its bar only while the mouse is free. While a host streams, the host-keys hook (`couch_platform_win::host_keys`, through `pipeline::Backend`) watches the physical keyboard for the panic key and the keys that answer requests. All shortcuts live in `couch_input::shortcuts`.
- **The host overlay** (M8). Requests and short notes about the session (watching, leaving, who plays, control paused) show in a corner over the game, on the monitor showing what is streamed, so the host needn't leave it:
  - **Answering:** Ctrl+Alt+Shift+Y accepts and N declines the oldest request, through the same hook as the panic key, so a guest's injected keys never count. A request must have been pending 1 s first.
  - **The window:** opened by the app's main window when there is something to show and closed when not (`useOverlay.ts`). It never takes the focus (no-activate, created unfocused; never hidden and shown again), clicks pass through it, and it is left out of captures (`WDA_EXCLUDEFROMCAPTURE`), so it never shows in a stream of the screen. It stays away while the app's own window is in front, which shows the same.
  - **The chime:** two tones made with Web Audio in the main window, for when the overlay can't show (true exclusive full screen).
  - **Settings → Overlay** turns either off.

## Lifecycle

How sessions survive things going wrong, or end clearly (M6):

| What happens | What the app does | Where |
|---|---|---|
| The game swaps its window (display mode, leaving a launcher) | The host follows the new window within the 5 s grace | `pipeline::source`, `couch_platform_win::game` |
| The game exits | The session ends with "the game exited", at once | same |
| The window closes, the game runs on | "Source lost" after the grace | same |
| A peer's app is killed or hangs, or the path dies | `Alive` stops; after 5 s the connection is closed as `timed_out` | `couch_net::control` |
| The connection to the host drops while watching | The stream window stays ("Reconnecting…"); watching resumes on the next connection if the session is the same, within 30 s | `rooms::sessions`, `pipeline::watch` |
| The stream window crashes | It is started again (at most once a minute), and asks for a keyframe | `pipeline::watch` |
| The host app panics | A panic hook lets go of every key and button it holds | `couch_platform_win::held_input` |
| The host app is killed while a guest holds a key | A marker file records what is held; the next start of the app or of `couch-cli host` lets go of it | same |
| The host app is killed while the host's controller is hidden (P2) | A marker file records what was hidden; the next start of the app or of `couch-cli host` shows it again. Until then the controller doesn't work in games | `couch_platform_win::hidhide` |

`couch-cli lifecycle-check` stages the game's cases, a killed host, and a host killed holding a key, and times each.

## Safety invariants

These hold in every milestone. Tests guard them from M2 on.

- Guests get gamepad permission only. Keyboard and mouse come only with a keyboard seat the host chose to set up and passed to them (P1).
- Keyboard and mouse are injected only while the captured game window is in the foreground.
- Remote members can't send the Windows key combinations, Alt+Tab, Alt+Esc, Ctrl+Esc, Ctrl+Shift+Esc, Alt+F4 (a guest quits through the game's menu), or the gamepad Guide button.
- A host panic key takes every seat back from the viewers and pauses control; it ignores injected keystrokes. The host's own controller keeps playing (P2).
- Every handoff, disconnect and teardown releases held keys and sends a neutral pad state first.
- Remote input reaches the injectors only through the seat router (`couch_input::router`), which enforces the rules above and the 300 ms dead-man release. So does the host's own controller when it plays a seat (P2).
- A controller the app hides from games is shown again when the session ends, and at the next start after a crash.
- Data from peers is size-limited and parsed defensively. Envelope frames are capped at 64 KiB and IPC frames at 16 MiB.

## Installing (M10a)

- **The installer** is Tauri's NSIS bundle, built by `scripts\build-installer.ps1` with the installer's own settings (`apps/desktop/src-tauri/tauri.installer.conf.json`, kept apart because Tauri's build copies bundled files next to the app it builds, which would overwrite development binaries). It asks whether to install for the current user (`%LOCALAPPDATA%\Programs\Couch Co-App\`) or for everyone (`Program Files`); on an administrator account Windows asks for administrator rights as it opens (NSIS's multi-user support). The app goes in that folder, with `couch-viewer.exe`, the FFmpeg and SDL3 DLLs and `drivers\` next to it, where the engine finds them. It registers `couchco://` links and adds a Start menu entry. Unsigned (ADR 0009: installers go to friends only), so SmartScreen warns.
- **The drivers are optional.** After the app installs, `installer-hooks.nsh` asks about each missing one (ViGEmBus, HidHide; found by their registered service), saying what won't work without it. A Yes runs the driver's own official setup, which asks for administrator rights. Their installers are pinned by SHA-256 in `xtask/src/deps.rs` and their licences ship beside them (`apps/desktop/src-tauri/drivers/`). Settings → Drivers shows their state and runs the same installers later (`couch_platform_win::drivers`). Uninstalling the app leaves them.
- **Builds that can't talk say so.** `PROTOCOL_MINOR` is the wire revision, for good (ADR 0009); a peer with another one is refused at `Hello`, and the member list says who needs to update.
- **Logs:** an installed (release) app logs to `desktop.log` in the profile folder, beside `viewer.log`; one older log is kept as `desktop.old.log`.
- **Licences** (M10b): the installer puts `LICENSE` and `THIRD-PARTY-NOTICES.txt` (`cargo xtask notices`) next to the app; Settings → About shows them. FFmpeg's pinned source and build scripts go beside the setup file, with `SOURCES.txt`. A release installer must come from a clean, committed tree, since its notices link to that commit's source.
- **Uninstalling** removes the app and keeps the profiles in `%LOCALAPPDATA%\CouchCoApp` (identity, rooms, settings, logs), unless "Delete the application data" is ticked (P4).
  - Tauri's box only knows its own folder, `com.couchcoapp.desktop`. So `installer-hooks.nsh` then also asks whether to delete ours, for the user running the uninstaller.
  - If a crash marker is waiting (a controller left hidden, keys left held), only the app undoes those, so the question advises No and starting the app once first. Yes still deletes.
  - Never during an update, nor in a silent run.
- **Release configuration** (M7): `build-installer.ps1` reads the private `release.toml` (outside the repository; `deploy/release.example.toml` shows its shape). It holds the relay's URL and token and the invite page, and the script passes them to the build as `COUCH_BUILD_*` variables. Without the file it builds only with `-TestRelay`: iroh's public relays, and plain http relays on the LAN allowed. Such installers are named `-test`.
- **The version** (0.8.0 for the first installer, 0.9.0 for M7's, 0.10.0 for M9 and P4, 0.10.1 for M9e's fix, 0.10.2 for M9f's capture, 0.11.0 for M12c, M19, M18 and P6, wire revision 4; 0.11.1 for the newcomer fix and P7, the same wire revision, so it still talks to 0.11.0; 0.11.2 for P8's bicubic scaling in the stream window; 0.11.3 for P9's physical controllers told from virtual pads, still wire revision 4; 0.12.0 for M23's several seats for the host, wire revision 5, so it doesn't talk to 0.11.x; 0.13.0 for M22's remapper pads as the host's controllers, still wire revision 5, so it talks to 0.12.0; 0.14.0 for M12a's pacing for hosts whose encoders take frames in memory, the same wire revision; 0.15.0 now: M13's profile backup, still wire revision 5, so it talks to 0.12.0 and later). From 0.11.1 on, every PR that changes the app bumps it itself (`cargo xtask bump patch|minor`, CLAUDE.md "Versions"), and each wire revision's version is in `couch_proto::REVISIONS`. It is the same in `Cargo.toml`, `tauri.conf.json` and `apps/desktop/package.json`; the build script checks. Updates are a new installer, installed by hand (no updater: ADR 0009).

## Platform limits

- Virtual gamepads on Windows need the ViGEmBus 1.22.0 driver, which is archived but still the only redistributable option. It sits behind the `VirtualPad` trait so a user-mode driver can replace it.
- **The host on a seat** needs HidHide (MIT; 1.5.230, May 2024), a driver installed once with administrator rights and a restart; the installer offers it, and Settings → Drivers installs it later (M10a). Our virtual pads report a real Xbox 360 controller's ids; since P9 a real Xbox 360 controller on the host is told from them by where it sits in Windows' device tree, and can play a seat like any other. Since M22 so can another program's virtual pad (a remapper's, DS4Windows's say), never ours; on one PC, a guest's stream window may read the controller behind the remapper too, so one press drives two seats (two PCs never do). On one PC, XInput's 4 slots are shared by the host's seat pads and everything else: with 3 or 4 seats an Xbox-style controller can get none.
- **Injection limits.** Elevated game windows, UAC prompts, the lock screen and anti-cheat titles reject injected input. A virtual gamepad still reaches an elevated game, but the panic key's hook doesn't see keys while it is in front (measured in M6). The host panel's stream list marks windows of programs running as administrator and warns when one is picked; Take back in the app still works.
- **Exclusive fullscreen.** True exclusive-fullscreen games may not capture through Windows.Graphics.Capture; a Desktop Duplication fallback (Sunshine has one) is left for later. They also draw over the host overlay (M8); the chime and the answer keys still work.
- **Older Windows.** Windows.Graphics.Capture grew its options over versions: hiding the yellow capture border needs Windows 11, and a minimum frame interval a newer Windows 11 still. Where one is missing, capture keeps Windows' default (the border shows around the window on the host's screen, not in the stream). Before this was handled, every stream from a Windows 10 host ended at its first viewer.
- **macOS.** Planned as a viewer and keyboard/mouse host only. System-wide virtual gamepads need an Apple-restricted entitlement.

## Native dependencies and licensing

- **FFmpeg.** The 8.1 LGPL shared build from BtbN, pinned in `xtask/src/deps.rs`. It is linked dynamically and its DLLs ship unmodified, so they stay replaceable. Its build config must not include `--enable-gpl` or `--enable-nonfree`, and `cargo xtask doctor` checks this.
- **FFmpeg bindings.** Its Rust bindings are generated once and committed (`cargo xtask gen-ffmpeg-bindings`, [ADR 0004](adr/0004-ffmpeg-via-rsmpeg.md)), so builds need no LLVM.
- **SDL3.** 3.4.16, Zlib license, prebuilt Visual C++ package.
- **libopus.** 1.6, BSD-3-Clause, compiled from source by the `opus` crate with CMake and linked statically. FFmpeg's build includes libopus too, but its wrapper can't ask for loss concealment.
- **The app** is GPL-3.0-only ([ADR 0008](adr/0008-gpl-3.0.md), `LICENSE`).
- **Crates.** Permissive licenses by policy, enforced by `cargo deny check` (`deny.toml`); a GPL-3.0-compatible copyleft crate needs a recorded exception.
- **FFmpeg stays the LGPL build** even though a GPL build would now be allowed: it ships unmodified and replaceable with fewer obligations. Switching (for x264, say) would be a deliberate decision.
- **GPL projects.** Sunshine and Moonlight are GPL-3.0, so their code may be reused, with its copyright notice kept, the source named where it's used, and a third-party notice. RustDesk is AGPL-3.0: ask first.
